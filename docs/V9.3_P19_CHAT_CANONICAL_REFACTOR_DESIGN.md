## 1. 方案 A：canonical-protected 重构（用户批准）

### 1.1 核心原则

1. **query-api 完成 JWT、tenant、cluster/resource scope 的服务端解析**；请求体与前端 header 不能覆盖可信身份。
2. **定义明确 capability**：
   - 当前 `/api/v1/ai/chat` 前端 `AiChat.tsx` 是**对话型**（intent=diagnosis，SSE streaming，suggestion/report），**不创建 Investigation Run**。
   - → 该路由只提供对话，使用**独立 `ai.chat`** capability，**不得**借 `ai.investigate` 绕过 ManualBoundary。
   - 若将来某个入口要创建 Investigation Run，必须走 `/internal/v1/run-invocations`（`ai.investigate` + ManualBoundary），由 `NewInvestigation.createRun` → `/api/v1/ai/runs` 触发。
3. **query-api 只向 orchestrator 转发由服务端生成的可信上下文**（`SignRunInvocation`），禁止 JWT fallback、客户端构造 Trusted Context、透传任意 tenant/principal。
4. **fail-closed 矩阵**：system principal、过期/重放上下文、JWT 与 body tenant 不一致、跨 cluster、无 capability → 全部拒绝。
5. **流式响应、断线重连、审计事件**保留身份绑定。
6. **迁移完成后**：P19.6 十问从前端经 query-api 实跑；随后 P19.8 Browser E2E。

### 1.2 关键架构判断：对话 ≠ Investigation Run

| 维度 | 对话型 `/api/v1/ai/chat` | 调查型 `/internal/v1/run-invocations` |
|------|------------------------|--------------------------------------|
| 前端入口 | `AiChat.tsx` (chatWithAI) | `NewInvestigation.tsx` (createRun → /api/v1/ai/runs) |
| capability | **`ai.chat`（新）** | `ai.investigate`（既有） |
| ManualBoundary | 不建 Run，无需人工触发约束 | 必须 user_explicit，拒绝 SystemPrincipal |
| 流式 | 必须 SSE 流式透传 | 非流式 `{run_id, events}` |
| 现有链路 | ProxyAI 错误地连到 run-invocations（**需改**） | 已正确 canonical（auth.go:581）|

> **审计发现（历史无效旧代码）**：现有 `ProxyAI` 对 `/api/v1/ai/chat` 的转发目标是 `/internal/v1/run-invocations`（settings.go:706），这**把对话路由错误接到调查入口**，若简单放开白名单，会导致：
> - 对话请求被要求 `ai.investigate` capability（viewer 无此 capability → 对话失败）
> - 对话请求触发 ManualBoundary 建 Run 语义（但 run-invocations 又 collect 非流式，与前端 SSE 期望不符）
> - 前端 `stream:true` 的 SSE 帧永远得不到（run-invocations 返回 `{run_id, events}` JSON）
> 
> 因此**不能**直接放开白名单放行现有 ProxyAI 行为；必须把 chat 重构为独立的 `ai.chat` + 流式 trusted ingress。

### 1.3 目标链路

```
Browser (AiChat) → query-api POST /api/v1/ai/chat (canonical-protected)
  → AuthMiddleware: JWT + MySQL tenant + 白名单放行
  → ProxyChat handler (新，替代现有 ProxyAI chat 分支):
      RequestAuthorizationContext → body 解析（message/intent/stream）
      cluster 解析 + tenant ownership（复用 ClusterDAO.ResolveRef）
      capability = ai.chat（独立）
      SignRunInvocation(principal_type=user, ..., capability=ai.chat) → 签名可信上下文
      → orchestrator /internal/v1/chat (流式 trusted ingress)
      → SSE 流式透传回 Browser（不缓冲）
  → orchestrator: verify_run_invocation_ingress → ai.chat capability 授权
      → brain.stream_sync(...) SSE 流式 → 逐帧回传 query-api → Browser
```

### 1.4 capability 定义

- 新增 `ai.chat` capability（仅对话，不建 Run）。
- `ROLE_CAPABILITIES`（orchestrator authorization_matrix.py）为各角色加入 `ai.chat`：
  - viewer / engineer / operator / admin 均可对话（对话仅消费只读工具，符合只读原则）。
  - 注意：对话内部若 Agent 调用查询工具，仍需各自 `observability.*.read` capability（Tool Registry 层已约束）。
- `ai.chat` **不等于** `ai.investigate`；对话不会创建 Investigation Run、不触发 ManualBoundary 建 Run 语义。

## 3. fail-closed 矩阵

| 场景 | 期望 |
|------|------|
| JWT 无效 / token 撤销 / user 非 active | 403 permission_denied（RequestAuthorizationContext）|
| X-Tenant-ID 非 canonical / 非成员 | 400 invalid_context / 403 |
| body 缺 cluster / cluster=all | 403 CLUSTER_ACCESS_DENIED（无默认回退）|
| cluster 不存在 / 非 tenant owner | 403 CLUSTER_ACCESS_DENIED |
| system principal / internal service 伪造 | 403（RequestAuthorizationContext 内部链拒绝）|
| body tenant ≠ JWT tenant | 403 TENANT_ACCESS_DENIED |
| 跨 cluster scope | 403 CLUSTER_ACCESS_DENIED |
| 无 `ai.chat` capability | 403 CAPABILITY_DENIED（orchestrator 授权层）|
| 签名缺失 / 过期 / nonce 重放 | 401/409（verify_run_invocation_ingress）|
| issuer 未配置（query-api）| 403 permission_denied（fail-closed）|

## 4. 流式与身份绑定

- query-api `ProxyChat` 用 `http.ResponseWriter` 实现 `http.Flusher`，把 orchestrator 的 SSE 帧逐帧 `Write` + `Flush` 透传，**不缓冲**（对齐 P10 公共 SSE proxy 已启用 `WriteTimeout=0`）。
- 身份绑定贯穿：Browser JWT → query-api 验签 + 签名 `ai.chat` 上下文 → orchestrator 验签 + capability 授权 → `brain.stream_sync(request_context=InvocationScope)` → SSE 帧。审计（principal/tenant/cluster/request_id）随事件结构保留。
- 断线重连：复用旧 ai_chat 的 `is_disconnected` 检测 + thread+queue 模型，断开即停止，不悬挂。
