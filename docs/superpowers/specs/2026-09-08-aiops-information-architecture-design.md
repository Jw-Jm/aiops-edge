# AIOps 云平台资源运维信息架构设计方案

**日期：** 2026-09-09

**状态：** 已按业务边界重新收敛，待实施

**产品定位：** 面向单一生产环境、多个 Kubernetes 集群的智能云平台运维平台。物理机、虚拟机、网络、存储、Kubernetes 对象和应用服务均严格归属于一个 Kubernetes 集群，平台以资源健康、故障调查和受控处置为主线。

**范围：** `observability-frontend` 的产品信息架构、全局上下文、资源模型、核心页面编排、知识图谱、视觉系统、响应式行为和验收标准；以及 `ai-apm-query-go` 为统一资源目录提供的最小、只读、增量查询模型。

**不在本轮范围：** 改变 `/me/scope` 授权语义、重写 Query API 或数据库、改变 Investigation/Action 持久化事实、替换 HugeGraph/G6、引入新的 UI 框架、增加自动执行权限。

## 1. 审核结论

上一版“工作台 → 调查 → 资源 → 观测 → 处置 → 报告”的运维闭环继续保留，但以下设计不再成立：

- 不再提供 `prod / staging / test / dev` 环境选择。平台只有生产环境，环境是固定属性而不是用户可切换 Scope。
- 不再把 Namespace 放入全局 Scope。Namespace 只属于 Kubernetes 资源域，可作为资源、分组或页面局部筛选条件。
- 不新增含义不明的全局“节点”选择器。物理服务器、Kubernetes 节点和虚拟化实例必须使用不同资源类型。
- 资源中心不再默认进入“服务全景”。默认首页改为当前集群的资源全景与异常资源队列。
- 现有服务、Kubernetes、虚拟机、硬件、容量和关系页不能仅通过 Tab 平铺后被称为资源中心；必须统一资源身份、归属、健康、依赖、变更和处置能力。

新版信息架构的核心是：

`登录租户 → 当前集群 → 可选统一资源 → 时间范围 → 观测 / 调查 / 处置`

其中集群是服务端授权根，统一资源是跨页面查询上下文，时间范围是普通页面的活动窗口；正式 Investigation 创建时将三者冻结为只读快照。

## 2. 产品目标与成功标准

### 2.1 产品目标

- 用户进入平台后 10 秒内知道哪个集群、哪类资源、哪个对象最需要处理。
- 从异常资源进入正式调查不超过 2 次点击。
- 任一问题都能回溯到具体资源或明确标注为集群级问题。
- 任一调查都能同时回答：影响对象、证据、AI 判断、缺失证据和下一步动作。
- 任一处置动作都能回溯到来源 Run、冻结资源、风险、预检、审批、执行和验证。
- 资源页面先回答身份、归属、健康、依赖和近期变化，再展示底层指标、日志和 Trace。
- 页面在 1440×900、1280×720、1024×768 下保持完整主任务路径和清晰视觉层级。

### 2.2 可验收指标

- 全站只存在一个可写的活动 Scope store；页面不得自行从 `localStorage` 读取活动集群或资源。
- Scope Bar 仅显示集群、可选资源和时间范围，不出现环境、全局 Namespace 或无类型节点。
- 集群列表只来自 `/me.available_clusters`，集群切换必须在 `/me/scope` 成功且 `/me` 回读确认后生效。
- 统一资源必须包含 `clusterId`、`uid`、`type`、`domain`、`name`；Kubernetes 资源可附带 `namespace`，但不能让它成为全局父级 Scope。
- 资源中心默认展示当前集群的计算、网络、存储、Kubernetes、应用服务五类健康概览和异常资源，不默认展示服务调用图。
- 工作台问题队列覆盖所有平台资源域，不把缺少服务名的数据丢弃或伪装为服务问题。
- Investigation 的 Resource、Evidence、Hypothesis、Root Cause、Action 都来自持久化 Run 数据，不使用演示数据或前端推断冒充事实。
- 处置中心按资源类型和服务端 capability 展示动作；没有能力声明时只读，不推断可执行动作。
- 知识图谱在默认视图下可读、可分层、可聚合，节点不重叠，标签不遮挡，颜色不单独传达状态，并提供等价文本列表。
- 所有列表、图、抽屉和详情都覆盖加载、空、错误、部分、陈旧、无权限六类状态。
- 三档视口通过布局与截图验收，无横向溢出、无关键语义截断、无未样式化 JSON 堆叠。

## 3. 设计原则

### 3.1 资源是平台主语

告警、指标、日志、Trace、变更、调查和动作都是资源的状态、证据或操作。页面标题和主要交互优先使用资源名称与业务含义，技术 ID 只作为辅助字段。

### 3.2 集群是唯一授权根

所有平台资源严格归属于一个 Kubernetes 集群。前端以 `/me/scope` 确认的 `tenant + cluster` 作为授权边界；资源选择只能缩小当前集群内的查询，不能扩大授权。

### 3.3 资源类型必须明确

禁止用“节点”“实例”“对象”等模糊词代替类型。界面分别使用“物理服务器”“Kubernetes 节点”“虚拟机”“Pod”“网络”“交换机”“存储卷”等业务名称。

### 3.4 先异常与关系，后原始信号

默认页面展示可判断的健康摘要、异常资源和主影响链；指标、日志、Trace 和完整图谱作为下钻内容。

### 3.5 Run 是正式事实容器

跨源证据、假设、根因、动作、审批、执行、验证和报告都归属于 Run。Chat 只做只读问答和调查草稿，不成为第二套事实源。

### 3.6 美观来自秩序与一致性

视觉不依赖大面积品牌色、阴影或装饰动画。美观来自稳定网格、清晰层级、合理留白、类型一致、状态明确和内容密度控制。所有状态必须既好看又可读，不能只有正常数据态经过设计。

## 4. 统一资源模型

### 4.1 资源域

平台资源分为五个资源域：

1. **计算**：`physical_server`、`k8s_node`、`vm`、`vmi`。
2. **网络**：`switch`、`switch_port`、`nic`、`network`、`nad`。
3. **存储**：`disk`、`storage_class`、`pv`、`pvc`。
4. **Kubernetes**：`namespace`、`deployment`、`replicaset`、`statefulset`、`daemonset`、`pod`、`container`、`k8s_service`、`endpoint_slice`。
5. **应用服务**：`business`、`application`、`service`、`middleware`。

`cpu`、`dimm`、`mainboard`、`bmc`、`psu`、`fan` 是物理服务器的组件，在物理服务器详情中展示，不作为资源选择器的一级结果。`alert`、`change`、`case`、`sel_event`、`migration` 是证据或事件，不作为可选资源。

### 4.2 稳定类型

```ts
export type ResourceDomain =
  | 'compute'
  | 'network'
  | 'storage'
  | 'kubernetes'
  | 'application'

export interface PlatformResourceRef {
  clusterId: string
  uid: string
  type: GraphEntityType
  domain: ResourceDomain
  name: string
  namespace?: string
}

export interface ActiveScope {
  tenantId: string
  clusterId: string
  resource?: PlatformResourceRef
  timeRange: TimeRange
}
```

约束：

- `resource.clusterId` 必须等于活动 `clusterId`。
- 集群切换成功后必须清空旧资源。
- 未选择资源表示整个集群，而不是“全部环境”。
- `namespace` 仅用于 Kubernetes 资源定位和局部查询兼容。
- Resource UID 使用知识图谱 `entity_uid` 或后端稳定资产 UID，不使用显示名称拼接身份。

### 4.3 与现有接口兼容

现有 Run/Chat 接口若仍要求 `environment`，前端适配器固定发送 `prod`，界面不显示选择器。现有 Run 接口若仍有独立 `namespace` 字段，只从所选 Kubernetes 资源的 `namespace` 投影，不能从全局下拉框产生。

本轮不修改数据库语义；新增 typed resource UI 模型后，通过边界适配函数映射到现有 `target_resource_id`、`resource_type`、`namespace` 和 `environment` 字段。

### 4.4 统一资源只读接口

资源中心不得在浏览器中拼接五套来源并自行推断资源身份。Query API 增加三个只读投影，复用现有图谱、本地资产和集群授权，不引入新的事实表：

- `GET /api/v1/resources/catalog?domain=&type=&q=&health=&limit=&cursor=`：返回当前授权集群内的 `PlatformResourceRef`、健康摘要、定位路径、数据来源和游标；不接受客户端 tenant，也不允许跨集群查询。
- `GET /api/v1/resources/summary`：返回五个资源域的总数、健康分布、异常数量、数据完整度和最后同步时间。
- `GET /api/v1/resources/detail?uid=<encoded entity_uid>`：返回资源身份字段、组件/绑定摘要、健康、数据来源和服务端 capability；不存在、跨集群和无权限使用不同错误码。

接口响应统一携带 `generated_at`、`partial`、`stale`、`warning_codes`。Catalog 和 Detail 的 UID、类型、归属与知识图谱 Graph DTO 保持一致；指标、日志、Trace、事件和容量明细继续使用原有接口，不复制到资源目录接口中。

## 5. 全局 Scope 与壳层

### 5.1 Scope Bar

固定顺序：

`集群 / 资源（可选） / 时间范围`

示例：

`生产平台 · cluster-a / 计算 · 物理服务器 · node-01 / 最近 1 小时`

“生产平台”是只读语境标签，可放在品牌区或集群选择器上方，不作为下拉控件。

### 5.2 集群选择器

- 展示集群名称、连接状态、节点数量和最近同步时间。
- 搜索匹配名称与 slug，不展示 UUID 作为主文本。
- 切换期间锁定资源选择器并显示明确进度。
- 服务端拒绝或回读不一致时恢复原集群，并用 `role="alert"` 展示错误。
- 单个可用集群仍显示只读名称，避免用户不知道当前操作边界。

### 5.3 统一资源选择器

- 支持按五个资源域分组、名称搜索、仅看异常和最近访问。
- 搜索结果显示类型、名称、归属路径和健康状态。
- 同名资源必须显示类型和定位路径，例如 `Kubernetes 节点 / node-01` 与 `物理服务器 / node-01`。
- 选择资源后，URL 使用 `resource=<encoded entity_uid>`；刷新和深链可恢复资源上下文。
- 资源不存在、跨集群或无权限时清空选择并明确提示，不回退到第一条资源。

### 5.4 时间范围

- 提供最近 15 分钟、1 小时、6 小时、24 小时。
- 普通页面使用相对时间；Run 创建时转换成绝对起止时间。
- 图表、表格和知识图谱摘要统一显示当前时间范围与最后更新时间。

### 5.5 Run Scope

Run 打开后显示灰色只读“调查快照”：

`集群 / 资源类型 · 资源名称 / 绝对时间窗口`

Run 页面不得调用 `setActiveScope`。用户可通过“在当前全局范围查看资源”进入资源中心，但该动作不能悄悄改写 Run 快照。

## 6. 信息架构

### 6.1 一级导航

1. 工作台 `/overview`
2. 调查 `/investigation`
3. 资源 `/resources`
4. 观测 `/observe`
5. 处置 `/actions`
6. 报告 `/reports`
7. 系统管理 `/admin`（仅管理员）

一级导航保留运维闭环，不按技术采集组件拆菜单。AI 助手继续作为全局入口，不占一级导航。

### 6.2 资源中心二级结构

- 集群全景（默认）
- 计算
- 网络
- 存储
- Kubernetes
- 应用服务
- 容量
- 关系探索

二级结构是资源域，不是组件或数据源名称。Grafana、VictoriaMetrics、VictoriaLogs、DeepFlow、HugeGraph 不进入资源导航。

### 6.3 旧路由兼容

保留现有旧深链重定向至少两个小版本，并把目标改为新的资源域：

- `/observability/service` → `/resources?domain=application`
- `/observability/relationships` → `/resources?view=graph`
- `/observability/vms` → `/resources?domain=compute&type=vm`
- `/infra/k8s` → `/resources?domain=kubernetes`
- `/hardware` → `/resources?domain=compute&type=physical_server`
- `/capacity` → `/resources?view=capacity`
- 观测、处置、报告和 Chat 的已有兼容路由继续保留。

## 7. 核心页面设计

### 7.1 工作台

首屏采用 12 栏网格：左侧 8 栏为“当前最重要的问题”，右侧 4 栏为“调查与处置”。普通资源数量和利用率 KPI 放到第二层，不抢占问题队列。

问题队列覆盖全部资源域，每项展示：

- 严重度、资源类型、资源名称和所属集群。
- 影响对象数量、持续时间、关键证据和数据质量。
- 近期变更、负责人、调查状态、处置状态。
- 与状态匹配的唯一主动作：开始调查、查看调查、查看处置或查看验证。

集群级问题明确显示“集群范围”，不伪造具体资源。资源域摘要使用五个紧凑分组，点击后进入资源中心对应域。

### 7.2 资源中心：未选择资源

默认首屏是集群资源全景：

1. 顶部显示集群身份、连接状态、采集完整性和最后同步时间。
2. 主区域显示跨资源域的异常资源队列，按严重度、影响面、持续时间和近期变更排序。
3. 次区域显示计算、网络、存储、Kubernetes、应用服务的健康分布与容量风险。
4. 底部显示近期变更、资源同步质量和跨域主影响链。

默认不渲染完整知识图谱，避免首屏成为不可读的节点云。

### 7.3 资源中心：已选择资源

桌面端使用“目录 + 详情 + 上下文”布局：

- 左栏 240–264px：资源域、类型、搜索、异常筛选和资源列表。
- 中栏弹性宽度：资源身份、健康摘要、关键指标、相关事件、日志/Trace 和近期变更。
- 右栏 304–336px：上游、下游、影响面、关联调查、可用动作和数据质量。

资源身份卡按类型展示真实字段：

- 物理服务器：厂商、型号、序列号、BMC、K8s 节点映射、组件健康。
- Kubernetes 节点：角色、版本、Ready、污点、容量、宿主物理服务器。
- 虚拟机：Namespace、节点、CPU/内存、磁盘、网络、迁移状态。
- 网络：类型、端点、连接资源、链路状态、吞吐、丢包与错误。
- 存储：类型、容量、使用率、绑定关系、访问模式、健康与扩容能力。
- Kubernetes 工作负载：Namespace、控制器、期望/就绪副本、Pod、Service、镜像与变更。
- 应用服务：业务、应用、Namespace、工作负载映射、调用健康和依赖。

没有服务端字段时显示“未提供”并标注数据来源，不使用统一的“未知 Namespace/Node”占位。

### 7.4 观测中心

观测中心是证据工具箱，不是资源目录。默认“问题”视图按当前集群或资源过滤，其他视图包括告警、指标、日志、Trace、事件和变更。

- 选中资源时，所有查询显示资源标签和过滤条件。
- 未选资源时，展示集群级聚合并明确范围。
- 数据源错误、部分结果、陈旧结果分别展示，不能降级为健康或空数据。
- Grafana 保留为专家入口，不成为默认观测体验。

### 7.5 调查中心与工作台

调查队列突出资源类型、资源名称、集群、症状、影响、阶段和负责人。Run ID 作为辅助字段。

新建调查继承当前 `cluster + resource + timeRange`，用户补充症状和动作模式后显式提交。来自问题、资源或 Chat 的草稿必须预填 typed resource，页面加载不能隐式创建 Run。

调查工作台继续使用三栏：

- 左栏：资源身份、影响链、冻结 Scope、相关变更。
- 中栏：Evidence 时间线和原始详情。
- 右栏：当前结论、候选假设、反证、缺失证据、建议动作。

图谱在调查中默认展示“主故障链”，不是完整邻居图。证据不足时显示 `insufficient_evidence`，禁止确定性根因措辞。

### 7.6 处置中心

处置中心由资源 capability 驱动：

- 物理服务器可出现硬件巡检、隔离建议等已接入动作。
- Kubernetes 节点可出现 cordon、uncordon、drain。
- Workload 可出现 rollout restart、scale 等白名单动作。
- 虚拟机、网络和存储只有服务端返回 capability 时才显示动作入口。

资源浏览页面只提供“建议动作/进入处置”入口，不内嵌审批和执行表单。所有动作统一进入动作中心完成预检、风险、审批、执行、验证和回滚审计。

### 7.7 报告

报告以资源事件为主语，包含资源身份、集群、影响链、证据、根因、动作、恢复验证和容量趋势。报告不得默认把所有事件称为服务故障。

## 8. 知识图谱视觉与交互设计

### 8.1 使用场景分离

知识图谱提供三种明确视图：

1. **资源关系**：查看当前资源一跳邻居和跨域归属。
2. **主故障链**：只显示与当前问题相关的传播路径。
3. **专家探索**：允许扩展深度、过滤类型和关系，但设置严格节点/边上限。

三种视图使用同一 Graph DTO 和视觉语义，不共享同一默认布局参数。

### 8.2 布局

- 资源关系使用中心资源固定的径向布局，一跳邻居按资源域分组。
- 包含、宿主和绑定关系使用自上而下的层级布局。
- 主故障链使用从左到右的 DAG 布局，异常源位于左侧，影响对象位于右侧。
- 专家探索默认从已选资源开始，首次只加载一跳；用户显式展开节点后再请求更多邻居。
- 默认最多显示 80 个节点、200 条边；超过上限按类型聚合并显示“还有 N 个”，而不是裁剪后静默丢失。
- 节点超过 50 个或用户启用减少动态效果时关闭布局动画。

### 8.3 节点视觉

- 节点使用“类型图标 + 两行标签 + 状态标记”，名称最多两行，完整值在 tooltip 和详情中展示。
- 节点填充以中性表面为主；资源域使用克制的分类色条或图标色，健康状态使用独立边框/角标。
- 选中资源使用交互蓝外环；严重、异常、风险、恢复分别使用红、橙、黄、绿并同时显示文字。
- 物理服务器、Kubernetes 节点、虚拟机必须使用不同图标和中文类型标签。
- 未知健康状态使用中性灰和“状态未知”，不能使用绿色。

### 8.4 边视觉

- `CONTAINS`、`HOSTS`、`RUNS_ON`、`USES_VOLUME`、`ATTACHED_TO`、`DEPENDS_ON` 使用稳定的中文关系标签。
- 结构/归属关系使用中性实线；依赖关系使用有向线；推测关系使用虚线；当前故障传播链才使用红/橙强调。
- 边标签在低缩放级别隐藏，放大或选中时显示，避免文字覆盖。
- 反向关系和候选方向必须由 DTO 明确提供，前端不能根据几何位置推断。

### 8.5 图谱控件与辅助视图

图谱工具栏固定提供：适应画布、放大、缩小、回到中心、全屏、层级深度、资源域过滤、关系过滤和图例。右侧上下文面板展示所选节点的身份、健康、邻居、影响、证据和可用动作。

图谱下方提供与当前图完全等价的“关系列表/主故障链列表”，支持键盘访问和屏幕阅读器。图谱不可用时保留资源详情与关系列表，不让页面整体失效。

### 8.6 图谱状态

- 加载：显示与最终布局尺寸一致的骨架，不显示旋转图标覆盖整页。
- 空：说明当前资源没有已同步关系，并提供“刷新同步”或返回资源详情。
- 错误：显示错误来源、重试按钮和 request ID（若服务端提供）。
- 部分：显示已加载节点/边数量、warning code 和截断原因。
- 陈旧：显示快照时间和“数据陈旧”标签。
- 无权限：不暴露隐藏节点数量或名称。

## 9. 全站视觉系统

### 9.1 页面骨架

- 左侧导航默认 216px；1280px 及以下自动收敛到 64px。
- 顶部第一行放全局搜索、通知、用户；第二行固定 Scope Bar。
- 页面内容使用 12 栏网格，最大内容宽度保持一致；主间距 20px，紧凑间距 12/16px。
- 页面标题区只保留标题、范围摘要、最后更新时间和最多两个主要动作。

### 9.2 色彩

- 背景 `#F5F7FA`，主表面 `#FFFFFF`，次表面 `#F8FAFC`。
- 主文本 `#172033`，次文本 `#5B667A`，边框 `#DDE3EA`。
- 交互蓝 `#3157D5`；严重红 `#C9362B`；异常橙 `#C46816`；风险黄 `#A46F0A`；恢复绿 `#18864B`。
- 图谱资源域分类色与健康状态色分离；分类色必须同时带图标/类型文字，不能单独表达语义。
- 禁止大面积渐变、彩虹卡片、装饰性阴影和无意义动画。

### 9.3 字体、密度和表格

- 基础字号 13px，页面标题 20px，关键数字 24px；正文行高不低于 1.5。
- 卡片圆角 8px，表格行高 44px，主要点击目标不小于 36×36px。
- 列表主列包含资源类型、名称和定位路径；技术 UUID 放到次级文本或复制操作。
- 表格列数超过可读宽度时优先隐藏辅助列并进入详情，不依赖横向滚动完成主任务。

### 9.4 图表

- 图表必须有标题、单位、时间范围、图例和数据来源。
- 同一指标在不同页面保持同一颜色、单位和小数精度。
- 不用面积渐变掩盖数据；异常区间用明确背景带或阈值线。
- 缺点、断点和无数据必须与零值区分。

### 9.5 全部显示状态

每个数据区域必须设计以下状态，尺寸尽量稳定以避免页面跳动：

- 骨架加载。
- 无资源/无结果空态。
- 来源错误与重试。
- 部分数据与缺失来源。
- 陈旧数据与快照时间。
- 无权限与所需 capability。

禁止直接把任意对象 `JSON.stringify` 成主界面内容。原始 JSON 只能在“原始数据”折叠区使用等宽字体、格式化、复制按钮和大小上限。

## 10. 响应式、可访问性与性能

### 10.1 响应式

- 1440px 及以上：资源详情保持 264px / 弹性 / 336px 三栏；图谱与详情并排。
- 1280–1439px：侧栏折叠；资源左栏 224px，右侧上下文 304px；辅助字段进入详情。
- 1024–1279px：资源目录变为 Drawer，上下文变为 Tab；主内容保持单列可操作。
- 低于 1024px：只读提示，禁止生产处置，本轮不承诺移动端完整操作。

### 10.2 可访问性

- Scope、资源目录、问题队列、Tab、图谱工具栏和关系列表可通过键盘遍历。
- 状态变化使用 `aria-live="polite"`，危险失败使用 `role="alert"`。
- 图谱容器有准确 `aria-label`；关系列表提供等价内容。
- 状态色同时配文字、图标或线型；对比度满足 WCAG AA。
- 支持 `prefers-reduced-motion`。

### 10.3 性能

- Scope 切换取消旧请求并按 `tenant + cluster + resource + timeRange` 生成 query key。
- 资源搜索防抖 250ms，最少输入 2 个字符；最近访问不触发额外全量请求。
- 图谱按需加载邻居，销毁时释放 G6 实例和事件监听。
- 大图禁用动画并聚合节点；页面切换不保留不可见图实例。

## 11. 权限、审计与安全

- 导航按信息可见性开放，危险动作按服务端 capability 控制；隐藏按钮不能替代服务端授权。
- Run/Evidence 延续 tenant + cluster + run 三元授权。
- Resource UID 必须属于活动 cluster；跨集群资源请求由服务端拒绝，前端不自动切换集群绕过。
- Action 读取和决策分权；只有 approver/admin 显示批准与驳回。
- 所有 Action 决策携带 `action_version` 和 idempotency key；资源版本变化要求重新预检。
- UI 不显示 provider URL、SQL、token、内部拓扑地址或原始异常栈。
- Chat、Investigation、Action 和资源同步身份保持分离。

## 12. 数据流

1. 登录后读取 `/me`，获得租户、活动集群和可用集群。
2. 用户切换集群，前端调用 `POST /me/scope`，再回读 `/me` 确认。
3. 集群确认后清空旧资源、取消旧查询并加载集群全景。
4. 用户从统一资源选择器或资源中心选择 typed resource。
5. 工作台、资源、观测和 Chat 继承活动 `cluster + resource + timeRange`。
6. 用户显式创建 Run，前端把相对时间转成绝对窗口并适配到现有 Run API。
7. Worker 产出 ToolRun、Evidence、Hypothesis、RCA、Graph Context 和 Action Proposal。
8. 调查详情通过权威快照和 SSE 更新；图谱只展示持久化 Graph Context。
9. Action 在处置中心完成预检、审批、执行与验证，状态回投 Run。
10. Run 完成后生成以资源事件为主语的报告。

## 13. 测试与视觉验收

组件测试至少覆盖：

- 环境和全局 Namespace 从 Scope 移除。
- 集群切换成功/失败、资源级联清理和跨集群资源拒绝。
- 资源域映射与 evidence/event 类型排除。
- 资源深链恢复和无权限资源清理。
- 资源身份按类型投影，不显示不相关字段。
- Chat/问题/资源到调查草稿的 typed resource 预填。
- Run Scope 冻结和现有 API 兼容适配。
- Action capability、版本、幂等和状态映射。
- 图谱布局模式、节点上限、聚合提示、状态语义、降级关系列表和实例清理。

Playwright 覆盖：

1. 切换集群 → 查看集群全景 → 选择物理服务器 → 查看硬件、关系和观测。
2. 选择 Kubernetes Workload → Namespace 局部筛选 → 创建调查草稿 → 显式创建 Run。
3. 选择虚拟机 → 查看网络与存储关系 → 转为正式调查。
4. Run 主故障链 → Action Proposal → 处置中心审批 → 执行/验证状态回显。
5. 图谱搜索 → 选择节点 → 展开一跳 → 过滤资源域 → 切换关系列表。

视觉回归采集 1440×900、1280×720、1024×768 下的工作台、集群全景、五类资源详情、观测中心、调查工作台、处置中心、报告和知识图谱。逐页检查：对齐、留白、层级、溢出、截断、状态色、图标、图表单位、空态、错误态、部分态、陈旧态和无权限态。

## 14. 迁移策略

1. 建立 typed resource 模型和 API 兼容适配，不改变现有授权与数据库语义。
2. 简化全局 Scope，加入统一资源选择器和深链恢复。
3. 建立集群全景与资源域目录，保留旧页面作为子视图过渡。
4. 改造类型化资源详情、工作台和观测过滤。
5. 重构知识图谱视觉、渐进加载和等价关系列表。
6. 将调查、处置和报告接入 typed resource。
7. 完成全站视觉统一、三档响应式和视觉回归后移除旧 Scope/UI 兼容代码。

每个阶段必须可独立发布并保留旧深链。迁移期间仍以 Query API、Run、Evidence、Action 和 Graph DTO 为权威事实，不新增并行事实源。

## 15. 非目标

- 不把平台扩展为多环境或多云账号管理产品。
- 不把 Namespace 提升为跨资源域层级。
- 不把所有资源强行塞进一个巨型表格或一张完整关系图。
- 不自动执行高风险动作，不扩大 AI 权限。
- 不为了页面饱满而伪造 Owner、健康、关系、容量或观测数据。
- 不在本轮提供低于 1024px 的生产处置体验。
