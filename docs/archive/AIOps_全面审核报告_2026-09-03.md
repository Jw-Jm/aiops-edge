## 二、问题清单

严重度定义：**P1** = 应尽快修复（安全/可靠性实质缺口或门禁失效）；**P2** = 建议修复（风险较低或为技术债）。

### 2.1 安全

**[P1-S1] rca.py:387-404 — kubectl 白名单漏拦输入重定向 `<`，可读节点任意文件**
`_run_kubectl_safe` 的危险字符正则为 `[;>&` $()\n]`，拦截了输出重定向与命令替换，但**没有 `<`**。管道工具白名单 `_ALLOWED_PIPE_TOOLS = {tail, head, sort, grep, tr, wc, awk, echo}`（rca.py:376）中 `sort`/`wc`/`grep -f` 均消费 stdin：形如 `kubectl get pods | sort < /etc/shadow` 的命令中，`<` 会覆盖管道 stdin，使 `sort` 直接输出任意文件内容并回显给调查会话。该函数是调查期自动执行的只读诊断路径，**无需审批即可触达**。
**建议**: 将 `<>` 一并加入拦截类（一行修复），并为 `_ALLOWED_PIPE_TOOLS` 每个工具限定参数形态。

**[P1-S2] ai-llm-egress-proxy/main.go:156 — PROXY_TOKEN 未配置时全代理无鉴权（fail-open）**
`if c.proxyToken != "" && proxyTokenFromRequest(r) != c.proxyToken`——令牌为空时跳过校验，但 provider API key 照常注入转发。任何网络可达者均可借代理消耗 LLM 额度。`/readyz` 会报未配置但不拦流量。同仓库 credential-broker（main.go:88-92）在生产模式缺配置时直接 `log.Fatal`，属正确姿势。
**建议**: `AIOPS_ENV=production` 下 proxyToken 为空即拒绝启动；非生产也应对 `/v1/proxy/*` 返回 503 而非放行。

**[P1-S3] deploy/scripts/apply.sh:73-75, 99, 108-114 — 一键部署默认弱密码并显式关闭首次改密**
ADMIN_PASSWORD 缺省回退 `admin1234`，同时 `--set queryApi.authRequireFirstLoginPasswordChange=false` 关闭了 values.yaml:374 默认开启的强制改密；JWT_SECRET 用可预测前缀 `dev-jwt-` 生成；所有密钥经 `--set` 明文传递（留存于 helm release 值、shell history、进程列表）；无环境守卫阻止在共享/生产集群执行。
**建议**: `AIOPS_ENV=production` 时对弱密码/关闭改密直接 fail；secrets 改用临时 values 文件注入并及时清理。

**[P1-S4] CI 无 push 触发 — 所有质量门禁可被直推 main 绕过**
`.github/workflows/aiops-workflow-gates.yml:3-16` 仅 `workflow_dispatch` + 限定路径的 `pull_request` 触发，而 git log 显示实际开发流为直接提交 main——**全部 gate 实际从未在这批提交上运行**。workflow 亦无 `permissions:` 最小权限声明、无 lint、无 `pip-audit`/镜像扫描。
**建议**: 增加 `push: branches: [main]`，声明 `permissions: contents: read`，补 ruff 与依赖审计步骤。

**[P1-S5] requirements.txt:1-16 — Python 依赖零锁定、无供应链校验**
全部 `>=` 开放下限（crewai>=1.0、chromadb>=0.4.24 等），无 lock 文件、无 hash pinning。CI 每次安装最新解析结果，构建不可重现，恶意上游版本可直接进入门禁与镜像；`sentence-transformers` 还拖入 torch 级重依赖。
**建议**: pip-tools/uv 生成锁文件，CI 固定按锁安装并跑审计。

**[P2-S6] 令牌比较非常量时间（Go 侧三处）**
- `ai-credential-broker/main.go:110-114`：`got == s.token`
- `ai-action-executor/main.go:261`：`X-Executor-Token` 直接相等比较
- `ai-apm-ingest-go/cmd/ingest/main.go:344`：`X-Api-Key` 直接相等比较

Python 侧（internal_ingress.py:182-185、shell_ws.py:70）均正确使用 `hmac.compare_digest`。计时侧信道在共享网络是低概率威胁，但修复零成本：Go 统一 `subtle.ConstantTimeCompare`。

**[P2-S7] approval_signature.py:41-52 — 审批签名 payload 未覆盖全部契约字段**
签名仅覆盖 `contract_id/actions/resources/expire_time` 四字段。若 contract 还含风险等级、参数细节等可变字段，它们不受 Ed25519 签名保护，"防篡改"承诺对未覆盖字段不成立。
**建议**: 对完整契约规范化 JSON 签名，或明确文档化哪些字段在签名保护内。

**[P2-S8] db_approval.py:77 — 动态列名拼 SQL 模式**
`UPDATE approval_tasks SET {', '.join(cols)}`，列名来自内部调用方而非用户输入，当前安全；但该模式被新调用方复用即成注入点。建议对列名做白名单断言。

**[P2-S9] ai-orchestrator/Dockerfile:33-55 — 镜像依赖 779MB 本地二进制且无校验和**
`COPY bin/sp.tar.gz`（422MB）、`chroma.tar.gz`（166MB）、`k8sgpt`（116MB）、`kubectl`（55MB）全部来自本地 `ai-orchestrator/bin/`。已验证这些文件**未进 Git**（git ls-files 为空，.gitignore 生效，历史无痕迹——这点正确），但 fresh clone 无法构建镜像，且 kubectl/k8sgpt 等 K8s 级权限二进制入库无 sha256 校验。`fetch-offline-deps.sh` 同样无校验和。
**建议**: 改受控镜像仓库拉取，或 fetch 脚本固化 sha256。

**[P2-S10] ai-event-collector/wal.go:47,51 — WAL 文件权限过宽**
目录 0755、文件 0644，事件数据（含消息正文）对节点上其他用户可读。建议 0750/0600。

**[P2-S11] 根目录 `:memory:.ses` 遗留产物 — 疑似内存库被静默落盘**
文件名强烈暗示某处代码把 SQLite `:memory:` 字符串当文件路径拼接了后缀写盘。内容仅为时间戳+uuid（无敏感值），`.gitignore` 已覆盖不会入库，但"内存库落盘"本身值得排查 session/checkpointer 初始化路径。

### 2.2 可靠性与正确性

**[P1-R1] db_approval.py:74-78 — 审批任务写入失败被静默吞掉**
`update()` 的 `except Exception: pass` 使 MySQL 抖动期间审批决策只存在于进程内存 dict：重启即丢、多副本互不可见。审批是执行链的授权依据，SoT 静默降级属可靠性缺口。
**建议**: 至少记日志；读路径在降级态显式标注"非持久/单副本"。仓库自己的 runtime-slo.md 明文"禁止空 catch 后返回成功"，此处应对照整改。

**[P2-R2] orchestrator.py:2480-2493 / tools.py:563-566 — 注释与实现漂移的死逻辑**
两处注释均写"已按产品要求放宽：shell=True 支持管道/重定向/换行"，但 shell_policy.py:45-48 早已重新拦截重定向/换行元字符——orchestrator.py 中 `script.splitlines()` 逐行执行实际永远只收到单行脚本。属于安全收紧后未清理的死逻辑 + **误导性安全注释**（更危险）：后人可能据注释"恢复放宽"。
**建议**: 删除逐行循环与过时注释，或将其改写为对当前策略的准确描述。

**[P2-R3] ai-apm-ingest-go/cmd/ingest/main.go:685-697 — 固定窗口限流器边界突发**
窗口重置瞬间可突发 2 倍 RPS。对"保护 ClickHouse"的目标而言建议换令牌桶或滑动窗口。

**[P2-R4] ai-apm-query-go/internal/bootstrap/http.go:23 — WriteTimeout=0**
ReadTimeout 30s / IdleTimeout 120s 已设，但 WriteTimeout 无限。慢客户端可长期占用连接。建议显式设值（SSE 端点可单独豁免）。

**[P2-R5] main.py:78-90 — LLM_MOCK 默认开启，靠启动时 fail 关闭**
`os.environ.setdefault("LLM_MOCK", "true")` 使**任何遗漏该变量的本地/预发部署都在演示假 AI 输出**；生产由 `AIOPS_ENV=production` + LLM_MOCK=true 时 SystemExit 兜底（main.py:88，这个 fail-closed 是对的）。风险在于"忘了设 AIOPS_ENV 的准生产"。建议默认值改为 false，本地用 compose/脚本显式开启。

**[P2-R6] investigator.py:4,55-56 — 注释/文档与默认值相反**
docstring 写"默认 true"，代码 `os.environ.get("INVESTIGATOR_ENABLED", "0")` 实际默认**关闭**（values.yaml:470 也为 "0"）。自动调查功能实际处于停用状态，与文档相反。
**建议**: 修正注释；若该功能已被 investigation_runtime 取代，直接标记 deprecated。

**[P2-R7] client.ts:31 — 前端每个请求 JSON.parse 整个 localStorage**
`readCurrentClusterId()` 在**每个** API 请求的拦截器里读并解析 `aiops-ui-v3`，大 store 下是持续的同步开销。建议 uiStore 内存态直接暴露当前 cluster。

### 2.5 值得肯定的亮点（审核确认，非宣传语）

1. **服务间零信任落地完整**：query-api→orchestrator、query-api→executor 两条方向链均为「方向性服务令牌（hmac.compare_digest / 常量时间比较）+ Ed25519 签名上下文（typ/iss/aud/kid/iat/exp）+ nonce 防重放缓存（internal_ingress.py:32）+ 能力绑定（错 operation 即 403，internal_ingress.py:168-169）」四件套，Go 签发端（auth/issuer.go、trusted_context.go:114 subtle.ConstantTimeCompare）与 Python 验签端有跨语言 fixture 测试对齐。
2. **WAL 实现教科书级**（ai-event-collector/wal.go）：写前 fsync（Append:105）、乱序 ack 水位、临时文件+原子改名 compaction、按 seq 幂等 replay、backlog 三指标（records/bytes/oldest age）全量暴露到 /metrics。
3. **retry 背压而非丢弃**（clickhouse.go:177-201）：重试队列满时生产者等待而非 drop-and-ack，与 runtime-slo.md "禁止 drop-and-ack" 的自定契约一致。
4. **LLM 边界治理**（orchestrator.py:110-245）：api_key 仅存进程内存单例、绝不入 checkpoint/state；生产模式强制 base_url 命中 egress proxy 前缀且 key==proxy token（orchestrator.py:193-197）；Semaphore(4)+共享有界线程池解决超时线程泄漏；失败占位符（`_is_llm_failure`）不得流入报告/案例库。
5. **执行侧多重门控**：execution_gate 分级 + Ed25519 审批签名（谁批准谁签名）+ executor TOCTOU 重读 UID/RV + `execution_unknown` 禁止盲重试强制 Reconcile + credential broker 短命 token（TTL≤300s）+ approved 模式强制验签公钥（main.go:277-281）。
6. **Helm 密钥 fail-closed**：`aiops.requireSecret` 拒绝空值/CHANGE_ME 渲染（_helpers.tpl:229-251）；TLS 证书明确由外部注入、chart 不生成私钥；NetworkPolicy ingress/egress 双 default-deny 且支持单组件灰度（networkpolicy.yaml），k8sApiCIDRs 缺失时直接 `fail` 渲染。
7. **权限收敛可验证**：CI 用渲染后 manifest 断言 orchestrator-ops ClusterRole 无 patch/create/delete/update verbs 且三个 legacy 开关为 "0"（verify-aiops-workflow-gates.sh:79-88）。
8. **前端安全姿态**：HttpOnly Cookie 认证、authStore 零安全状态持久化、无 XSS 面（唯一 dangerouslySetInnerHTML 渲染静态常量）、SSE 有界重连+Last-Event-ID 防丢失、useAsyncData 过期请求守卫。

## 三、架构审核

### 3.1 服务拓扑与职责边界

```
Browser ──Cookie──> query-api-http ──> MySQL (IAM/Run/Chat/Action SoT)
                       │  │  │
                       │  │  └─> LLM egress proxy ──> deepseek/openai（唯一出站）
                       │  └────> credential broker ──> K8s TokenRequest（≤300s token）
                       └───────> ai-orchestrator（签名上下文 ingress）
query-run-dispatch ──lease──> Action outbox ──签名上下文──> ai-action-executor ──> K8s
investigation-worker ──签名 Run invocation──> orchestrator
event-collector ──WAL──> unified ingest ──> ClickHouse / VictoriaMetrics / VictoriaLogs
```

审核确认：**README 声称的服务边界与 Helm 模板、代码实现三者一致**。角色表（docs/architecture/index.md）中每条"禁止职责"在代码层有对应机制支撑：query-api 三角色拆分（deployment.yaml:14,59,104）、orchestrator 无生产写凭据（写凭据只在 broker/executor）、ingest 是唯一 CH 写入口（collector 只推 ingest，clickhouse.go 注释明确 runtime 不做 DDL）。

**结论：服务层架构健康，是本项目最强的部分。** 数据所有权（MySQL 归 query-api、编排域归 orchestrator，db.py:53-56 迁移器注释引用 SCHEMA_OWNERSHIP.md）有明文且有代码自觉。

### 3.2 数据流可靠性模式

| 链路 | 模式 | 审核结论 |
|---|---|---|
| 事件采集→CH | WAL + 内存 retry + 背压 + 幂等 replay | ✅ at-least-once 完整落地 |
| Run 创建→执行 | MySQL outbox + lease claim（ai_action_outbox.go:53-70，乐观 fencing：claim 带过期回收）| ✅ 防双发 |
| 执行结果 | execution_unknown → reconcile 状态机 | ✅ 防未知写盲重试 |
| orchestrator 内部 | lease-aware executor + 可恢复 Run | ✅ worker 崩溃可续 |
| 前端实时 | SSE + Last-Event-ID + 有界重连 | ✅ 断线不丢 |

短板：审批任务持久化（P1-R1）是上述体系中**唯一**静默降级点，与整体水准不匹配。

### 3.3 orchestrator 单体（主要架构债务，见 P1-A1）

123 个顶层平铺模块中混有：V2 生产链路（investigation_runtime/rca_engine/execution_*）、legacy 链路（investigator/flow_engine 直连 mutation/rca legacy）、纯工具（evidence_hub/intent_engine）、以及 demo/测试辅助（multicluster_demo）。新旧边界**只靠 4 个环境开关 + CI 渲染断言**维持，没有物理隔离。在开关矩阵正确时生产安全可控（CI 有真实断言），但任何一次"顺手把 values 改成 1"都会静默复活 legacy mutation 路径——**建议以删除代替关闭**。

### 3.4 部署架构

Helm chart 覆盖 30+ 组件，审核确认：NetworkPolicy 双向 default-deny + 出站依赖矩阵注释与各 Service targetPort 逐条核对过（chart 内注释自证）；mTLS 由 `mtls_server` 包装 uvicorn（deployment.yaml:48-49，--ssl-cert-reqs=2 即双向认证）；initContainer 等 query-api ready 才启动 orchestrator。灰度路径（egress canary）、备份 Job、graph schema migrator job 齐全。**部署架构成熟度高**，唯 apply.sh 弱密码默认（P1-S3）与 bin 离线二进制（P2-S9）拉低可复现性。

### 4.2 关键功能的"真实性"审核

这是本项目做得**好**的方面——每个 AI 功能都有防"假智能"设计：

- **NL2SQL**（main.py:4025）：LLM 不可用时降级到关键词模板生成白名单 SQL；SQL 执行前过 `nl2sql.py:66 validate_sql`（仅 SELECT、表白名单带库前缀、禁多语句/表函数/INTO OUTFILE），且**执行时二次校验**（main.py:4119-4121，防存储层污染）——双层校验是超出常见水准的。
- **LLM Mock 防混淆**：mock 输出带可识别占位符（`_is_llm_failure`），不得流入报告/案例库；生产禁止 mock（main.py:88 fail-closed）。唯默认值方向值得商榷（P2-R5）。
- **RCA 非黑箱**：确定性七维加权打分（rca_engine/scorer.py:7-9 权重显式）+ 矛盾规则降级（contradictions.py：症状之后发生的变更被标记 blocking）+ policy 文件 sha256 digest 绑定版本——结论可复现、可审计。
- **证据真实性**：LLM 推理绝对不能成为 Evidence（evidence_hub.py 铁律 F3），provenance 指纹去重。
- **Agent 工具白名单**：dual_agent.py:12 Coordinator/worker 工具循环均有显式白名单集合，spawn_worker 是唯一额外授权。

**未发现"演示型假功能"**（硬编码假数据、前端自嗨式 mock）。前端 api 层无 mock 数据文件，测试 fixture 全部隔离在 *.test-fixtures.ts。

### 4.3 功能层缺口（非缺陷，为 roadmap 建议）

1. **告警→调查的自动化闭环偏保守**：intent_engine 明确"Alert/Event 仅预填 scope，不自动创建 Run"。作为 Phase7 定位是合理的安全选择，但若产品期望"告警自动触发预调查"，需要补 approved_system_event 的完整链路。
2. **investigator（定时自动巡检）实际停用**（P2-R6）：文档写默认开启、代码默认关闭、values 显式 "0"。需要产品决策：要么修复启用，要么删除模块。
3. **执行动作类型有限**：executor 支持 patch/scale/restart/reconcile 等白名单操作，回滚框架（rollback_framework.py/gray_rollout.py）齐备但依赖 reconcile 结果——复杂拓扑（跨服务依赖链）的自动回滚编排未见实现。
4. **多租户配额/成本可见性**：LLM 代理有审计记录（谁/何时/哪个 provider），但未见按租户的 token 用量归集与限额。
