# AIOps 智能可观测平台 — 全面深入使用与改进建议报告

- **测试日期**: 2026-08-18
- **测试环境**: http://localhost:30253（演示环境，admin/admin123）
- **测试方式**: 真实浏览器自动化（Playwright）逐页/逐 Tab/逐弹窗实测 + 前端源码逐模块审计 + 后端 API 数据逻辑核验 + 真实 LLM（deepseek-v4-flash）自然语言运维对话实测
- **覆盖范围**: 全部 7 大板块、22 个路由页面、全部 Tab、弹窗/抽屉/对话框、命令面板、AI Dock、通知抽屉、AI 对话全流程

## 一、总体结论

平台功能覆盖面广、产品逻辑主线清晰（观测 → 诊断 → 决策 → 执行闭环），AI 对话在"完整诊断"场景下表现优秀，能产出结构化、有依据、可执行的根因分析与处置方案，并具备"人工审批 → 安全执行"的闭环。整体处于**可演示、可试用**水平，但存在若干**数据一致性、AI 工具调用可靠性、交互细节**问题，距离"生产级运维可用"仍有差距。

**核心亮点**
- AI 完整诊断流程（集群健康巡检）输出质量高：能识别单节点风险、OOMKilled、Pod 重启、告警交叉印证，并给出处置命令与风险等级。
- 处置闭环安全设计到位：AI 建议 → 二次确认弹窗（展示命令+风险）→ 审批 → 执行，符合运维安全要求。
- NL2SQL 翻译准确（自然语言 → 合法 ClickHouse SQL），执行结果正确。
- 命令面板（⌘K）、AI Dock、通知抽屉等交互设计完整。

**核心短板**
- AI 对话对"工具调用"（k8sgpt、知识库 RAG）不可靠：明确要求用 k8sgpt / 参考知识库时，返回的是同一段泛化服务列表，未真正调用工具。
- 多处数据不一致（容量页 0.00% vs 总览 56.7% 内存；日志页展示 ClickHouse 内部查询日志等）。
- 大量页面静默失败（加载失败与"无数据"无法区分）、无错误提示/重试。
- 分页多为"客户端分页 + 固定拉取条数"，数据量大时"下一页"静默失效。

## 二、模块逐项实测与审计

### 1. 总览 / 工作台首页（/overview）

**实测内容**: 4 个统计卡（服务数量 11、调用总量 125,557、请求错误率 0.00%、P95 延迟 22.7ms）、资源态势（CPU/内存/磁盘进度条 + ETT 预测）、节点资源 TOP5（orbstack，CPU 17.37%、内存 56.49%）、调用与错误趋势图、活跃告警（1 条：容量预测 ETT 即将触达阈值，warning，40 次）、数据采集中断告警条。

**数据逻辑问题**
- **数据采集中断告警条**（"检测到数据采集中断：3 个时段无数据"）与"请求错误率 0.00%"并存，提示数据采集本身不完整，但页面仍展示"健康"统计，存在误导。
- **服务数量 11 vs 拓扑 13 服务**：总览统计卡显示 11 个服务，而服务全景/图谱显示 13 个服务，口径不一致。
- **错误率 sparkline 画的是错误次数而非错误率**（Overview/index.tsx:104），与"请求错误率"卡片标题不符。
- **服务数量与调用总量共用同一 sparkline 数据**（:102-103），两个不同指标显示相同趋势。
- **集群名映射 hack**（:43）：`c.id === 1 ? 'default' : c.name`，硬编码特殊处理，脆弱。
- 活跃告警仅统计 `limit:200` 内的数据。

**UI/UX**: 布局清晰、信息密度合理；但告警表格 min-width 900 在窄屏需横向滚动；节点/告警行为可点击 div，无键盘可达性。

### 2. 可观测 — 服务全景（/observability/service）

**实测内容**: 拓扑视图（12 节点 · 15 关系，力导向图，可拖拽）+ 服务列表视图 + 命名空间筛选 + 服务详情抽屉（健康分、Apdex/响应时间/错误率/吞吐率、指标趋势、调用关系、调用链/Span 明细 Tab）。

**数据逻辑问题**
- **时间窗口硬编码 24h**（:81），无用户控制；源码注释承认 trace/log 为种子数据，1h 窗口会全零。
- **错误率单位不一致（最可能真实 bug）**：`describeNode`（:32）按 0–1 小数判断，表格（:464）按 `error_rate*100` 百分比渲染。若后端返回 0–100 值，会误判所有服务异常且表格放大 100 倍。
- **节点大小用 `calls % 40`**（:100），0 调用服务也有 30 尺寸，非有意义缩放。
- **力导向布局 O(n²)×300 次迭代**（:249-287），大拓扑性能风险；重叠节点用 `Math.random()` 抖动，布局不可复现。
- **Trace 时长优先取 `max_ms` 而非 `duration_ms`**（:444）。
- 加载失败静默清空（:168），与"无数据"无法区分。

**UI/UX**: 拓扑为 canvas，不可键盘操作；图表高度 `calc(100vh-220px)` 在矮屏脆弱。

### 9. 容量预测（/capacity）

**实测内容**: 节点选择、预测窗口（12/24/48h）、CPU/内存/磁盘三卡片（当前值/阈值/环比/预计触达阈值 + 趋势图）。

**数据逻辑问题（实测确认）**
- **实测 bug：内存/磁盘显示 0.00%**，与总览页 56.7% 内存矛盾。后端 `/capacity/forecast` 返回 `current:0, history:[], timestamps:[]`（空数据），前端把 null 渲染成 0.00%，误导用户以为真实 0%。
- **实测 bug：无法区分预测范围是"整个集群"还是"集群中某个节点"**。页面节点选择器（Capacity.tsx:109）只有"全部节点"与具体节点两个选项，但：
  - **范围语义不透明**：选"全部节点"时 `instance=''`，后端 `capacityPromQLForCluster`（capacity.go:77-91）不加 instance 过滤，PromQL 用 `avg(...)` 对全部节点做**集群级聚合**；选具体节点时才按 `instance="..."` 过滤到**单节点**。但页面卡片标题（"CPU 使用率 · 当前值"等）与图表**均不显示当前范围**，用户无法判断看到的是集群聚合值还是单节点值。
  - **"全部节点"标签误导**："全部节点"实际含义是"集群级聚合（所有节点平均）"，而非"逐节点查看"，语义混淆。
  - **节点选择器来源混杂**：选项来自 `getCapacityInstances()`，可能是 node-exporter 的 instance 标签（如 `192.168.139.2:9100`）或 k8s 节点名（如 `orbstack`），两种来源混在一起，用户难以识别。
  - **集群维度缺失**：页面依赖全局集群选择器（currentClusterId）但**不展示当前数据属于哪个集群**，也无法在同一视图对比"集群级 vs 节点级"。
- **硬编码 `hours:72`**（:52），与所选预测窗口（12/24/48h）无关，预测窗口只改预测长度不改历史长度。
- **硬编码阈值**（:9-13）：cpu 80 / memory 90 / disk 85，不可配置。
- **ETT 只读 ewma 预测**（:16-33），线性预测的 ETT 被忽略。
- 环比 `change_pct>0 → danger` 硬编码假设。

### 11. 智能运维 — AI 对话（/ai/chat）

**实测内容**: 会话侧栏（新对话/清空/删除）、AI 对话主区、快捷提问（分析集群根因/集群巡检/服务延迟排查）、SSE 流式输出、处置建议卡片（确认执行/驳回/输出最终版本报告）、自定义命令执行。

**实测 AI 行为（真实 LLM）**
- ✅ **完整诊断场景质量高**："请分析当前集群的健康状况" → 输出结构化 Markdown 报告：识别单节点无冗余、OOMKilled 82 次、metrics-server/coredns 反复重启、orders 服务错误率、Deployment 不可用 43 次，给出处置命令与风险等级 0.40，并生成"处置建议·待确认"卡片。
- ✅ **实体校验智能**："分析 order-svc 错误率突增的根因" → 正确识别 order-svc 不存在，交叉引用 orders 相关告警，给出排查命令。
- ✅ **处置闭环**：确认执行 → 二次确认弹窗（展示命令+风险等级）→ 审批 → 执行。
- ❌ **k8sgpt 未真正调用**："请用k8sgpt诊断当前集群有哪些问题" → 仅返回"当前共有 10 个服务在运行"的泛化列表，**未调用 k8sgpt MCP 工具**。
- ❌ **知识库未真正调用**："我的Go服务内存持续增长导致OOM，可能是什么原因？请参考知识库" → 返回与上一条**完全相同**的泛化服务列表，**未检索知识库**（知识库中明明有 Go 内存泄漏案例）。

**数据逻辑问题（源码审计）**
- **会话重载丢失数据（bug）**（:107-117）：loadSession 只保留 role/content，丢弃 suggestion 消息的 kind/plan/script/threadId/riskScore/riskReason，重载后处置卡片退化为纯文本。
- **绕过 axios**（:156-159）：手动读 localStorage token 和 baseURL，与拦截器重复且脆弱。
- **消息时间戳扁平化**（:112-113）：所有消息用会话创建时间，非逐条时间。
- **无 Markdown 渲染**（:390-392）：LLM 输出的标题/列表/代码以纯文本 pre-wrap 显示，可读性差。
- **`chatWithAI()` 是死代码**（client.ts:108-112）：定义但未使用，实际用裸 fetch。

### 13. 智能运维 — AI 工具（/ai/tools）

**实测内容**: NL2SQL 查询 / MCP 工具 / 技能目录 / 市场 四个 Tab。

**实测结果**
- ✅ **NL2SQL 翻译准确**："近24小时各服务的调用量和错误率" → `SELECT service_name, count() AS call_count, round(countIf(is_error=1)/count()*100,2) AS error_rate FROM observability.trace_spans WHERE start_time >= now() - INTERVAL 24 HOUR GROUP BY service_name LIMIT 100`，执行返回正确结果（各服务 0% 错误率）。
- ✅ **MCP 工具 8 个**：query_metrics / query_traces / query_topology / get_service_list / **k8sgpt_diagnose** / deepflow_status / execute_shell / get_infrastructure。
- ✅ **技能目录 8 个**：告警处置 / 自动化运维执行 / 服务诊断 / 基础设施巡检 / 可观测性分析 / 历史案例检索 / 根因分析 / 虚拟机运维。

**数据逻辑问题**
- **技能目录只读**（:151-156）：API 有 `executeSkill` 但无执行入口，技能无法从页面运行。
- **sourceType 是装饰性的**（:242-247）：市场安装选"Tarball/Git URL"只改 placeholder，请求只发原始 source 字符串，选择无实际作用。
- **MCP 参数全为字符串**（:122-125）：数字/布尔参数按字符串发送，无类型转换。
- **SQL 兜底把整个响应当 SQL**（:41）：后端无 sql 字段时把整个对象 JSON 显示为"SQL"。

### 14. 智能运维 — 工作流（/ai/workflows + Editor + Detail）

**实测内容**: 工作流卡片（完整诊断流程 13 节点/12 边、交互诊断流程 6 节点/5 边，均已启用，暂无运行记录）、NL 生成、新建、运行抽屉、可视化 DAG 编辑器（React Flow，节点面板/配置抽屉/边配置/运行/审批/运行记录）。

**数据逻辑问题**

- **编辑器无图校验**：保存/运行前不校验是否有触发器、图是否连通、必填配置是否填全。
- **onRun 双重请求**（:432-458）：runWorkflow 后立即 getFlowRun 再 pollRun，若立即 getFlowRun 抛错会误报"运行失败"。
- **轮询 1500ms 无上限**（:416）：后端不返回终态会无限轮询。
- **无未保存离开提示**。
- **硬编码风险阈值**（:824）：>=6 红、>=3 橙。
- 新建工作流用固定 3 节点模板（trigger.manual → collect → summarize）。

## 三、跨模块共性问题

1. **静默失败普遍**：几乎所有页面 `.catch(() => setData([]))`，加载失败与"无数据"无法区分，无错误提示/重试（ServiceObservability:168、Trace:62、VirtualMachines:41、Overview:48-54、Knowledge、Report 等）。
2. **分页多为"客户端分页 + 固定拉取"**：Trace（50 vs 20）、LogMetrics（100 vs 20）、AlertEvents（200）、Knowledge（50 无 onChange）、Report（100）、Changes（200）——数据量大时"下一页"静默失效。
3. **时间窗口硬编码/无统一抽象**：ServiceObservability 24h、LogMetrics limit、Overview limit 200、Capacity hours 72。
4. **时间戳格式假设脆弱**：多处 `slice(5,16)`、`Number(v)*1000` 假设秒/ISO 格式，后端格式一变即错。
5. **可访问性不足**：ECharts canvas、可点击 div（Grafana 卡片、VM 行、Overview 行、图谱节点）无键盘可达性/role。
6. **固定宽度抽屉不响应式**：Approvals 720、Report 560、AlertEvents 560、ServiceObservability 620。
7. **cluster_id 注入全局端点**（client.ts:32-45）：拦截器给 /users、/ops/tasks、/ops/audit-logs 等全局端点也注入 cluster_id，多集群时可能静默缩小结果。
8. **角色词汇不统一**：admin/approver/普通成员 在不同页面口径不一。
9. **死代码/重复 API**：chatWithAI、updateAlertRule、executeSkill、legacy /ai/flows、ACTION_BY_KIND 重复等。

## 五、AI 对话专项评估（真实 LLM 实测）

| 场景 | 实测结果 | 评价 |
|---|---|---|
| 集群健康巡检 | 结构化报告：单节点风险、OOMKilled 82 次、Pod 重启、orders 错误率、处置命令、风险 0.40 | ✅ 优秀，有依据可执行 |
| order-svc 根因 | 正确识别服务不存在，交叉引用 orders 告警，给出排查命令 | ✅ 智能 |
| 处置闭环 | 建议 → 二次确认弹窗（命令+风险）→ 审批 → 执行 | ✅ 安全设计到位 |
| 要求用 k8sgpt | 仅返回泛化服务列表，未调用 k8sgpt | ❌ 工具调用不可靠 |
| 要求参考知识库 | 返回与上条完全相同内容，未检索知识库 | ❌ RAG 未触发 |
| NL2SQL | 翻译准确、执行正确 | ✅ |

**结论**：AI 对话的"完整诊断 + 处置闭环"主流程质量高、符合运维预期；但**工具调用（k8sgpt、知识库 RAG）触发不稳定**，是当前最需改进的 AI 能力点。建议在对话中显式回显工具调用过程与结果，提升透明度和可信度。
