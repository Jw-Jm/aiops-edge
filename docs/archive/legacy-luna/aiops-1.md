# 一、这份方案到底要做什么

当前系统是一堆互相独立的页面和能力堆在一起：可观测页面、AI Chat、AI 工具、工作流、知识图谱、Grafana、报告中心、容量预测。用户要自己点来点去、自己选工具和流程，才能拼出一套运维动作。

方案要把它改成：用户从"问题 / 告警 / 专业页面"进入后，平台自动规划调查、自动调用真实数据、自动形成可审计根因、自动生成结构化处置方案、走风险与审批、执行、再验证业务是否真正恢复。**普通用户不需要理解 LangGraph、MCP、K8sGPT、RAG、Tool Registry 这些技术能力。**

一句话：从"技术能力集合"收敛为"一条调查—处置—验证主链"的任务驱动智能运维控制面。

# 二、两条固定的用户主旅程

**旅程 A（从问题到根因）**：用户在服务页看到订单服务错误率上升 → 点击"交给 AI 调查" → 平台冻结租户 / 集群 / 服务 / 时间窗 → 识别 RCA 意图 → Planner 先查指标定位异常窗口 → 日志 / 链路 / 容器 / 变更并行调查 → 知识补充 → Evidence Hub 建立事实链 → Hypothesis RCA 产生、反证、补证并排序 → 最终根因 + 置信度拆分 + 未知项。用户全程不需要选择工具、代理、工作流、K8sGPT 或 RAG。

**旅程 B（从根因到恢复）**：根因确认或支持 → 生成结构化处置动作 → 风险引擎打分 → 按风险等级确认 / 审批 → 执行已批准且未变化的动作 → 观察窗口 → 对比前后指标、可用性、就绪副本、SLO → 判定成功 / 部分 / 失败 / 恶化 → 恶化则停止自动链并建议回滚 → 成功调查生成待审核 Incident Candidate。

# 四、核心架构原则（修正后）

## 4.1 双向可信上下文（P0-1，最大偏差修正点）

**必须区分两个方向的 Context，绝不能让"权限"作为授权事实被当作上下文传递。**

**方向一：Browser → query-api → orchestrator（创建调查 Run 的入口）**

浏览器只持有最小身份令牌。query-api 依次做：验证身份令牌 → 查询数据库用户与会话 → 查询数据库租户授权 → 解析规范集群 → 签发一个签名的 **RunInvocationContext** 传给 orchestrator。

RunInvocationContext 只包含：请求编号、主体编号、会话编号、租户编号、目标集群范围（本次调查请求的目标 scope，**不是用户全部授权列表**）、来源、签发时间、过期时间。

**绝对不传**：角色、权限列表、全部允许集群、是否管理员。

**方向二：orchestrator → query-api（Agent / Tool 实际查数据时）**

Agent 或 Tool 要查数据时，orchestrator 用服务身份 + 签名签发一个**短时的 TrustedRequestContext** 传给 query-api。query-api 依次：验证服务身份 → 验签 → 校验过期 / 受众 / 签发者 / nonce → 查询数据库实时授权 → 才放行实际数据访问。

TrustedRequestContext 包含：版本、签发者、受众、请求编号、运行编号、主体类型、主体编号、会话编号、租户编号、集群编号（不可变 UUID）、能力（如"可观测日志读"）、来源（如日志代理）、签发时间、过期时间、nonce。

**默认过期时间不超过 60 秒，每次工具调用新签一个。**

这样整个链路前后逻辑才完全一致：内层 Context 只回答"这次请求代表谁、请求哪个 scope、属于哪个 run"，**不回答"他有哪些权限"**。权限一律由 query-api 在每次数据访问时通过 MySQL 实时裁决。

## 4.2 授权来源（P0-2）

**JWT 只承载最小身份声明**：用户编号、会话编号、签发时间、过期时间、签发者、受众。

**授权事实全部来自 MySQL 实时查询**：用户是否活跃、会话是否有效、是否已授权某租户、角色是什么、权限是什么、是否已授权某集群、以及命名空间 / 资源 / 动作级授权。

**必须删除 JWT 内的任何授权事实**：角色、scope、租户 scope、集群 scope、是否管理员。

前端本地存储的角色只用于展示，服务端每次都要重新裁决。**禁止用前端按钮隐藏或 localStorage 承担授权语义。**

## 4.3 真多租户 schema（P0-3）与多对多授权（P0-10）

数据库 schema 与授权引擎从第一天就支持多个租户。**当前环境只初始化一个租户**，其租户编号是**生成的 UUID**，slug 为 default。

**用户与租户是多对多关系（P0-10）**：用户身份全局唯一，通过 `user_tenants` 与 `role_scope_assignments` 授权。**禁止为同一自然用户在每个租户复制账号。**

核心关系模型固定为：users、tenants、roles、permissions、user_tenants、role_permissions、role_scope_assignments、tenant_clusters。`role_scope_assignments` 表示：主体、角色、租户、集群（可选）、命名空间（可选）、资源（可选）；permission 决定 action。这支撑五级授权：租户 → 集群 → 命名空间 → 资源 → 动作。

**JWT / session 不承载 authoritative tenant scope（P0-11）**：请求选择 tenant scope，query-api 每次从 MySQL 校验。UI 可保存最近 tenant，但只是 UI 状态，不是授权事实。

禁止：租户编号固定为 1；租户编号缺失时回退到 1；"当前只有一个租户所以不实现多租户"。

## 4.4 集群身份三级规范（P0-6）

- **cluster_id** = 不可变的规范 UUID。所有数据库外键、指标标签、日志资源身份、链路、拓扑、事件、告警、证据、AI 运行、审批、执行、审计，一律用 UUID。
- **slug** = 全局唯一的人类可读引用（如 prod-sg-01）。**不得用 slug 作为资源身份。**
- **name** = 可变展示名（如"新加坡生产集群01"）。

**Canonical Resource Identity 不包含 tenant_id（P0-8）**。tenant_id 是 ownership / authorization / data isolation 维度，不是资源固有身份。cluster_id 已是不可变、全局唯一 UUID，资源身份只基于 `cluster_uuid + namespace + type + name` 构造：

```text
service:<cluster_uuid>:<namespace>:<service>
pod:<cluster_uuid>:<namespace>:<pod>
deployment:<cluster_uuid>:<namespace>:<deployment>
node:<cluster_uuid>:<node>
```

数据库记录层面才带 `tenant_id + cluster_id + resource_id`。这样 tenant 权属改变时 resource_id 不跟着改变。**不得使用 slug。**

## 4.4b Service Identity（P0-12）

query-api ↔ orchestrator 之间的服务间认证，V1 固定为：**Service Credential + 短时 Signed Context**。

- Service Credential：来自 Kubernetes Secret、与 Context signing key 分离、可轮换、不写数据库明文、不回传 browser、**不等同于 user authorization**。
- Trusted Context 证明"这个 service 正在代表 principal X 发起 run/tool request"；MySQL 决定"principal X 当前到底有没有这个权限"。
- **当前阶段不引入 SPIFFE / Service Mesh / 全套 mTLS**。代码抽象 `ServiceAuthenticator`，以后可替换。
- Kubernetes ServiceAccount 不是完整的服务间委托认证。

## 4.5 数据存储边界（P0-4，第二个重要偏差修正点）

存储职责边界固定为：

- **VictoriaMetrics** = 原始指标 Source of Truth。
- **VictoriaLogs** = 原始日志 Source of Truth。**ClickHouse 不保存第二份完整原始日志。**
- **ClickHouse** = 链路 / RED / 拓扑，以及派生的可观测分析（如 LogPattern、日志异常聚合）。
- **MySQL** = 授权 / 控制面 / AI 运行时持久化。
- **MinIO** = 大对象证据 / 知识对象。
- **Chroma** = 知识向量索引。

因此新数据模型**不能写成"所有可观测数据都是 SQL 表"**。第 4 阶段要定义的是 VictoriaLogs 的标签 / 结构契约（租户、集群、资源编号、命名空间、服务、容器、节点、级别、消息、链路编号、跨度编号、来源），原始消息留在 VictoriaLogs。LogPattern、日志异常聚合、首次出现、基线计数、当前计数、增长比例等派生数据才进 ClickHouse。

**禁止原始日志双写 VictoriaLogs + ClickHouse。**

## 4.6 AI 运行时所有权（P0-5）

- **orchestrator = AI 运行时业务语义 owner**：决定运行、计划步骤、工具运行、证据、假设、处置动作、验证、审批决策、AI 审计事件**什么时候产生、状态怎么推进、事件语义是什么**。
- **query-api = MySQL 持久化 owner**：负责结构、事务、数据访问层、租户隔离、数据库写入、查询，通过内部控制面接口提供。orchestrator **不维护第二套 MySQL Repository**。
- 平台自身的操作日志由 query-api 独立产生，与 AI 审计事件分离。

## 4.7 统一资源身份

Canonical Resource Identity 基于 `cluster_uuid + namespace + type + name`，**不含 tenant_id**（见 4.4）。不同集群里同名服务必须得到不同编号，不能串数据。解析编号用的是**确定性规则**，不用大模型。

## 4.7b Kubernetes Access Boundary（P1-13）

Agent / Planner / Tool **不得创建 Kubernetes Client、读 kubeconfig 或直接 kubectl**。只读通过 query-api Kubernetes Read Adapter；写通过 Execution Adapter。Kubernetes Access Boundary 是唯一能解析集群凭据引用的模块（见 P1-12），orchestrator 永远不能拿到凭据内容。

## 4.8 唯一工具注册中心

所有工具通过唯一注册中心调用，返回统一结果，结果里必须明确状态：成功、部分、无数据、失败、超时、不可用、没权限。不能再用空数组、空值、报错文本、自然语言承担状态语义。调用流程：检查可用性 → 校验参数 → 风险与只读门槛 → 超时 → 调用 → 规范化 → 持久化证据。工具参数不能接受与可信上下文冲突的集群；所有证据固定集群。只读属性和风险等级由代码注册，大模型不能修改。**禁止把一个工具包装成一个代理。**

**最低生产 Tool 清单固定（P1-17）**：query_metrics、query_logs、query_traces、query_alerts、query_topology、query_k8s、k8sgpt_diagnose、knowledge_search、query_changes、execute_k8s。Planner 不得临时发明工具。`execute_shell` 存在但 risk=R4、planner_selectable=false、automatic=false，不属于默认生产调查工具集合。

## 4.9 Evidence 是现场事实唯一来源

大模型只负责规划、解释、提假设，不能编造现场事实。无数据、不可用、没权限、超时，都必须如实反映，**绝对不能说成"系统健康"**。**LLM inference 不能独立成为 Evidence source。**

## 4.10 假设式根因分析

根因分析要讲证据：根据证据生成假设，看哪些证据支持、哪些反对、还缺哪些证据，缺了就补查一轮，最后排序。置信度要能拆开看，大模型判断权重不超过一半，低于及格线不自动修复。关键证据缺失时根因状态是"未知"，不能硬说成"确认"。

## 4.11 结构化运行记录模型

用结构化运行记录模型代替旧的聊天状态。一次调查的完整过程——计划、工具调用、证据、假设、根因、处置、审批、执行、验证——都要持久化，有固定状态机，重启后能恢复。检查点只用于运行时断点恢复，不作为业务历史真源。

## 4.12 固定事件推送协议

所有事件有明确类型、单调序号、时间、集群和结构化内容，每 10 到 15 秒发一次心跳，断线后按最后序号续传回放。前端不能靠解析大模型的文字去猜状态。错误分类准确：连接断开只表示客户端连接，运行真实状态要重新读；大模型超时、工具超时、后端错误、没权限、用户中止，都不能统一成网络错误。禁止用增大单个超时掩盖没有心跳、没有恢复的问题。

## 4.13 处置闭环

写操作必须先形成结构化处置动作，然后算风险，按风险分级走确认或审批，执行前冻结资源版本防止被改，执行后必须做前后对比验证。命令执行成功不等于业务恢复，发现恶化必须停下来并建议回滚。生产主路径只允许结构化处置动作；受限 Shell 只作为 R4 人工应急能力。

## 4.14 多租户多集群严格隔离

**所有 tenant/cluster scoped 的运行数据、可观测数据、Evidence、Run、Action、Audit 必须带 tenant_id / cluster_id（P0-9）**。但 `users / roles / permissions / tenants / clusters / system_config` 等控制面实体**不能被错误强制加 cluster_id**。跨集群聚合必须由服务端授权，不能让用户用"全部"来绕过权限。新写入信号能解析成规范身份，或明确标记部分 / 未知；身份缺失但信号可存时标记部分并记录缺失字段，禁止瞎猜集群和命名空间。

**跨集群内部 Context（P1-14）**：多集群调查必须拆为**每集群一个单独 TrustedRequestContext**；禁止 `cluster=*`、`allowed_clusters=[...]` 形式的内部万能凭据。

**System-triggered investigation（P1-15）**：告警自动调查使用 `principal_type=system`，不得伪造管理员 user。System principal 权限仍由 MySQL / Policy 管理；V1 自动触发默认只读。

## 4.15 删除所有双主路径

不允许旧聊天和新调查并存、旧规则分支路由和新注册中心并存、旧纯提示词根因和新证据型根因并存、旧会话检查点业务模型和新的运行记录模型并存。**新路径上线的那一刻，同一 Phase 内必须把旧路径删掉。**

# 五、实施阶段（最终后移编号）

> 说明：以下 Phase 编号为**最终后移版本**。历史文档、注释、Task、Gate 中凡是引用"Phase 16 数据清理"或旧编号的，一律以后移后的编号为准。**正式数据清理固定在 Phase 17。**

## 第一阶段：冻结基线，画出真实地图

**不修改任何代码、不删除任何文件、不动依赖、不重建数据**，只做记录和盘点。

- 记录当前状态：分支、提交号、最近提交、部署环境。
- 系统盘点五个自研服务、镜像构建文件、依赖清单、部署配置、数据库表、路由、页面、测试。
- 产出六份记录：一份重构前基线记录，加五份地图——代码地图、接口地图、数据地图、页面地图、依赖地图。
- 纪律：只记录、不修复。命令失败就记录失败（含命令、退出码、失败原因），绝不把失败写成通过。工具缺失、环境不可用，如实记成"不可用"，不记成"通过"或"零数据"。
- **真实可用性探测（P1-18）**：必须实际探测，配置存在 ≠ AVAILABLE。最少检查：MySQL、ClickHouse、VictoriaMetrics、VictoriaLogs、ChromaDB、MinIO、K8sGPT、LLM Provider、Kubernetes API、Docker、Helm、Playwright、Go、Python、Node.js。结果只有 AVAILABLE / UNAVAILABLE / UNKNOWN。禁止"配置存在 → available"、"命令不存在 → 0 data"、"接口 403 → no_data"。
- 安全：全程不得读取或打印任何密钥明文、凭据内容、令牌、数据库密码，只记录其存在性、名字、来源。
- 门禁：能回答当前有哪些服务、入口、页面、接口、数据链路、谁管哪张表、依赖、镜像大小；六份记录完整；未改动任何生产代码、配置、运行数据。
- 禁止：拿旧审计报告当新基线；因测试失败顺手改代码（此阶段只记录）。

## 第二阶段：定架构、定数据所有权、冻结契约

- 解决数据所有权冲突：审计表被两个服务各建一份、事件采集服务自建表但没进统一初始化、集群凭据明文存在数据库。
- 关键决策：AI 运行时表与 AI 审计事件，业务语义归 orchestrator，MySQL 持久化归 query-api；平台操作日志由 query-api 独立建表写入。两者不混。
- 新增架构文档与数据模型重设计文档；指定每张表的建表方、写者、读者、过期清理策略。
- 明确查询服务是浏览器唯一业务入口，编排服务只接受查询服务注入的可信上下文。
- 冻结核心契约：统一上下文、资源引用、工具定义与结果、证据、假设、处置动作、验证结果、意图、计划、步骤。跨语言保持一致、可序列化。
- **把 Source Reliability 默认值表固化为契约的一部分**（见第七节，直接采用已冻结数值，不重新设计）。
- 生成合法与非法输入样例，非法输入必须被拒绝。校验错误返回稳定错误码，不抛内部异常堆栈。
- 测试覆盖三端：编排服务契约测试、查询服务序列化测试、前端类型检查。
- 门禁：契约与所有权文档通过自审，所有契约测试通过。契约未冻结前，禁止开始实现代理、根因分析、界面主流程。

## 第三阶段：多集群信任边界与资源身份

- 实现双向可信上下文（见 4.1）。JWT 只承载最小身份（见 4.2）。所有 handler 使用统一可信上下文。
- 集群注册改造：使用不可变 UUID、slug、name 三级规范（见 4.4）；凭据从数据库明文改为引用，由密钥提供。
- **显式废弃四项旧机制**：JWT 角色 / scope、固定默认集群（id=1 → default）、隐式集群回退、`X-Tenant-ID` 权威授权语义。
- **X-Tenant-ID 生命周期（P1-11）**：Phase 3 起它彻底失去授权语义，只可暂时作为 requested scope；Phase 12 前端迁移后，Phase 14 必须删除旧 Header compatibility path，不能永久留着。
- **credential_ref 格式（P1-12）**：每 cluster 一个独立 Secret；MySQL 只保存 `k8s-secret://namespace/name` 等引用；首选 Secret key `kubeconfig`。只有 Kubernetes Access Boundary 可以 resolve，orchestrator 永远不能拿到内容。
- 新增资源解析接口，只返回调用者有权访问的规范资源；集群创建更新只接受凭据引用，不回传凭据内容。
- 错误语义明确：上下文非法、没权限、资源不存在、集群不可用、资源有歧义，分别对应不同状态码。
- 验证：两集群同名服务得到不同资源编号；没权限用户传"全部"或点名无权集群必须被拒绝，不能返回空列表假装成功。
- 让资源身份贯穿数据模型：所有新写入信号解析成规范身份；身份缺失标记部分并记录缺失字段；禁止 LLM 解析资源编号。
- 门禁：所有新写入信号能解析成规范身份或明确部分 / 未知。

## 第四阶段：干净数据模型与统一初始化

- 所有数据表结构收进统一初始化脚本：链路、日志、拓扑、告警、资源事件。采集服务不再自己建表，运行账号无建表权限。新增版本化结构记录和初始化校验。
- **日志存储边界固定（见 4.5）**：VictoriaLogs 是原始日志唯一主存；ClickHouse 只存派生分析。定义 VictoriaLogs 的标签 / 结构契约，而不是把原始日志建进 ClickHouse。
- 链路记录：租户、集群、资源编号、链路编号、父链路、服务、容器、节点、操作、耗时、状态、来源。
- 日志记录：租户、集群、资源编号、时间、命名空间、服务、容器、节点、级别、消息、来源、属性（在 VictoriaLogs）。
- 拓扑：来源与目标资源编号、命名空间、关系类型、时间窗、调用量、错误量、延迟、来源。
- 资源事件：事件编号、资源版本、次数、原因、类型、上报来源、涉及资源、首次与末次时间。
- 告警：补租户、资源编号、调查关联字段。
- 指标：统一标签，围绕租户、集群、资源编号、命名空间、服务、容器、节点组织。
- AI 运行时表：一次运行、计划步骤、工具运行、证据、假设、处置动作、验证、审批决策、AI 审计事件。审批审计表关联运行编号、租户、集群、动作摘要。证据大对象存对象存储，表里只留不可变引用与摘要。持久化失败不得把内存任务标成功，返回后端错误并可安全重试。
- 门禁：数据面和 AI 控制面都能从空库初始化出完整结构；配置表不受清理影响。禁止写旧表升级脚本；禁止长期运行服务自己建表。

## 第五阶段：重构采集链和事件采集服务

- 链路与日志采集切到新结构。深流数据租户不再硬编码默认，端点配置绑定规范集群。拓扑写入来源目标命名空间与资源编号。
- **保留写前日志机制**：写前追加、确认、重放、压缩、有界重试、健康检查、优雅退出。这是可靠性底线。
- 采集响应包含接收 / 拒绝数量、请求编号、结构版本；"成功接收"不代表查询立即可见。
- 错误语义：格式非法、未授权、压力过大、存储不可用但日志可接收、日志都写不了，分别对应不同状态。
- 事件采集服务：监听容器事件与 IPMI 传感器日志，写入统一资源事件表，记录事件编号、资源版本、次数、上报来源、规范资源编号。监听做单领导者、单一部署，避免每节点重复监听整个集群。新增写前日志或持久化发件箱，断点键为租户 + 集群 + 来源。移除服务启动自建表，改用统一结构。
- 错误语义：被拒绝不能当成"当前没有事件"；监听超时要重连；存储不可用保持积压并反映降级。
- 门禁：采集服务不自建表；重启或短时存储故障不丢已接收事件；重复率和积压可观测。

## 第六阶段：查询接口与统一调查查询层

- 把查询服务改造成统一调查事实查询层，让人工智能代理和前端页面共用同一套底层事实，不各自拼 SQL 或直连存储。
- 新增调查接口：资源、指标、日志、链路、拓扑、告警、容器、变更。统一响应：状态、摘要、数据、来源信息、错误。
- 错误语义：无数据返回无数据，没权限返回没权限，后端不可达返回不可用，查询超时返回超时。
- 现有查询函数抽成可复用层，调查接口不复制 SQL。
- **内部接口固定为 `/internal/v1/...` + 类型化 JSON 结构 + 契约测试**；只有破坏性变更才新增 v2（见 P1-10）。
- 改造 AI 代理的信任链：query-api 解析并签发可信上下文，把身份、租户、集群 scope、运行请求编号传给 orchestrator（见 4.1）。禁止原样透传前端伪造内部头、租户、超范围集群。浏览器只访问查询服务，内部令牌和可信上下文不回传浏览器。
- 编排服务超时、断流、拒绝、下游错误必须保留分类，不能统一成网络错误。
- 门禁：从浏览器到编排服务的身份、租户、集群、权限链可审计，且不能被前端伪造。禁止前端直连编排服务。

## 第七阶段：可信人工智能核心

- 建工具注册中心和证据中心（见 4.8、4.9）。工具状态准确：成功但结果为空 = 无数据，二进制缺失 = 不可用，被拒绝 = 没权限，检索成功但空 = 无数据，存储不可用 = 不可用。
- 建意图引擎、计划器、结构化状态。意图引擎识别用户想做什么、解析目标、判断需要哪些能力。计划器是唯一调查控制器，生成带依赖关系的计划，支持并行、缺证补查、取消。页面上下文与告警上下文进入意图。目标有歧义返回"资源有歧义"并让用户选择；缺关键证据生成"缺证"，不强行确定根因。计划器只能选择注册中心里且当前上下文可用的工具，不能通过提示词生成新执行能力。
- **Planner 硬预算（P1-3）**：初始步骤不超过 12 个；补查不超过 2 轮；总步骤不超过 20 个；工具默认超时 30 秒、长查询 60 秒、大模型 90 秒、整个运行 900 秒；大模型瞬态重试 2 次、只读工具瞬态重试 1 次、**写操作重试 0 次（写超时禁止自动重试，必须先查询实际状态）**。
- 结构化状态把旧自由文本字段全部收敛成固定结构：上下文、消息、意图、计划、工具结果、证据、假设、根因、处置、审批、执行、验证、报告、错误。
- 门禁：工具定义、工具结果、证据、意图、计划器、结构化状态契约测试全通过。禁止继续扩散临时字符串状态字段。

## 第八阶段：领域代理与资源图

- 建七类领域代理，各自只负责自己的专业范围。输入是计划步骤 + 上下文 + 已有证据，输出是工具结果列表、证据列表、缺失证据，**不能直接输出最终根因**。
  - 可观测代理：异常窗口、各项指标。
  - 日志代理：日志模式归一化、基线对比、增长、首次出现、与链路容器服务关联。
  - 链路代理：错误与慢链路、关键节点、正常与异常差异、下游异常。
  - **Kubernetes Agent（P1-2）**：覆盖 Deployment / StatefulSet / DaemonSet / Pod / Node / Event / Probe / Scheduling / PVC / 资源请求限制 / 重启 / 内存溢出 / 崩溃循环；K8sGPT 只是它的一个工具，不是独立代理。
  - 变更代理：部署版本、镜像、配置、容器事件、平台变更。
  - 知识代理：手册、案例、架构文档，保留来源与适用性。
  - 基础设施代理：只分析现有接入的节点、虚机数据，缺传感器数据输出"未知"，不许生成模拟健康结论。
- 七类代理默认只读，写操作只能输出处置动作草案。每个代理保留部分、无数据、不可用、没权限状态，不能汇总成成功。
- 建资源图，统一容器、链路、深流、服务元数据关系。
  - **第一版图模型（P1-1）固定为**：Cluster、Namespace、Node、Deployment、Pod、Service。Container 只作为附加元数据或 Pod 的元数据，**不能用 Container 替代 Pod，必须有 Namespace**。
  - 关系类型固定：runs_on、managed_by、belongs_to、calls、depends_on。
  - 输出给计划器、根因分析和前端嵌入，不是独立主入口。接口固定：上游、下游、运行时资源、所有者、依赖。
  - 图关系不完整返回部分并说明缺哪种来源，不靠大模型补边。跨集群关系默认禁止；图遍历每一步做范围过滤，避免通过边泄露未授权资源。
  - 禁止只把旧图谱改个名字而不解决身份、范围、来源问题。
- 门禁：计划器能从服务自动解析容器、节点、上下游；专业页面可按权限嵌入图。

## 第九阶段：假设式根因分析、补查与排序

- 建假设引擎。把现有确定性根因能力——拓扑关系、变化关联、容器命令假设证伪——改造成假设生成、支持、反驳提供者。
- 流程：证据 + 时间线 + 资源图 → 生成假设 → 支持、反驳、缺证 → 补查 → 评分排序 → 根因候选 + 未知项。计划器根据缺证添加补查步骤并重新评分。
- 根因输出必须带支持证据、反驳证据、未知项。关键证据缺失时根因状态是"未知"，禁止强行转成"确认"。假设不能引用其他集群证据。大模型训练知识只能标记知识或推断，不能当现场事实。禁止把"大模型一次调用直接返回最终根因"作为核心实现。
- **置信度与评分（P1-4、P1-5，已冻结）**：
  - 基础分 = 大模型推理先验 × 0.35 + 证据支持 × 0.30 + 来源可靠度 × 0.20 + 时间相关 × 0.15。
  - 最终分 = 基础分 − 反驳惩罚 − 关键证据缺失惩罚。
  - confirmed：最终分 ≥ 0.80 且至少一条高可靠直接证据且无关键反驳。
  - supported：0.60 ≤ 最终分 < 0.80。
  - unknown：最终分 < 0.60 或关键证据缺失。
  - rejected：反驳明显压过支持。
  - **最终分 < 0.60 禁止进入自动处置。**
  - high-reliability direct evidence 定义：可靠度 ≥ 0.85 且证据类型属于现场直接 / 确定性派生观测。因此 Runbook 即使非常匹配也不能单独把假设推成 confirmed。
  - **Source Reliability 默认值表**（见第七节，直接采用已冻结数值）。可靠度表示"来源默认可信程度"，不是事实最终置信度；"restartCount=15" 可带 0.95，但"因此 ConfigMap 修改是根因"是推断，不能继承 0.95。知识 / K8sGPT 永远不能覆盖当前运行事实，优先级：现场直接证据 > 现场派生证据 > 诊断工具 > 知识 / 历史案例 > 大模型推断。数值锁定在版本化配置，Luna 只能实现，不能为让测试通过而调高；调值必须走真实数据集校准 → 比较准确率误报率 → 改版本化配置 → 回归 12+ RCA 场景。
- 新增统一时间轴与"第一异常事件"检测器，把变更、容器事件、日志模式、链路异常、指标异常、告警合并成时间线，输出第一异常事件及其证据编号。告警不能默认当根因。时间戳不一致或时钟偏差过大时时间轴标记部分或未知。未授权证据不参与评分。
- 门禁：固定 RCA 场景在单测层完整验证 Intent → Plan → Tool → Evidence → Hypothesis → Missing → Additional → Root Cause → Confidence → Unknowns。禁止只测最终文字。

## 第十阶段：运行持久化、事件推送与恢复

- 建统一运行记录模型。任务、大模型图、调查使用同一持久状态机；检查点只用于运行时断点恢复，不作为业务历史真源。
- 固定运行状态：已创建、规划中、调查中、等待审批、执行中、验证中、成功、部分、失败、恶化、已取消。状态转换必须事务化、可审计、幂等。
- 接口覆盖：创建、查询、取消、事件回放。重复请求编号返回原运行；非法状态转换返回冲突；持久化失败返回不可用；已取消运行不能继续执行。运行上下文不可变，换集群就建新运行。进程重启后可恢复未完成运行；历史查询不依赖旧检查点。禁止为旧人工智能历史写转换器。
- **职责边界（P1-6）**：orchestrator = 唯一运行状态机 owner + 事件语义 owner + 序号分配器；query-api = 控制面持久化 + 运行 / 事件读投影 + 授权边界。**query-api 不自行推进运行状态**（如把"调查中"改成"等待审批"）。取消流程：query-api 授权取消 → orchestrator 做状态迁移 → query-api 持久化。
- 建新事件推送协议：固定事件类型、单调序号、心跳、结构化错误、结束事件。断线按最后事件序号恢复并回放。长任务不因断线取消后台运行，除非用户明确取消。事件回放重新鉴权，不能靠猜运行编号读别人证据。
- 门禁：长调查无静默断流；前端断线可恢复；错误分类准确。

## 第十一阶段：结构化处置、风险、审批、执行、验证

- 建处置动作、风险引擎、审批。所有写操作先生成结构化处置动作。风险引擎同时考虑动作本身、根因置信度、影响范围、运行环境。
- 风险五级：只读、诊断、重启扩容、配置资源部署修改、破坏性操作。行为对应：只读自动、诊断自动加审计、重启扩容用户确认、修改审批、破坏性严格审批或禁止。
- 审批决策绑定运行编号、动作摘要、目标、集群、资源版本、有效期、审批人。批准内容不能被替换。低置信度、过期审批、摘要不一致、资源版本变化、范围变化，都拒绝执行并返回稳定错误码。写动作必须单集群、精确资源，禁止"全部"。大模型输出不能直接成为命令，适配器只接受结构化参数。命令白名单、敏感路径、审计继续生效。禁止只按命令字符串判断风险。
- **审批自禁规则（P1-19）**：R3/R4 默认禁止自审批，包括管理员（action requester == approver → DENY）。超级管理员有审批能力也不意味着可批准自己的 R3/R4 动作。Break-glass 不属于 V1 普通审批路径，需单独设计、单独审计。Approval 必须绑定 action hash、cluster、target、resourceVersion、expiry。
- **Verification 按 Action Type 配策略（P1-20）**：Action Definition 必须包含 VerificationPolicy，按动作类型配置 success criteria、threshold、observation window、regression condition（例如 restart 关注就绪副本/就绪/重启数/错误率/延迟；scale 关注期望副本/可用副本/延迟/错误率/饱和度；rollback 关注部署版本/就绪副本/错误率/延迟/关键告警）。不能所有动作共用一个固定观察时间。
- **受限 Shell 定位（P1-7）**：生产主路径只允许结构化处置动作；受限 Shell 仅保留为 R4 人工应急能力，不属于计划器默认工具，代理不得自动选择，结构化动作失败不得自动回退到 Shell，必须人工显式触发，并有严格命令策略、审批、超时、审计、凭据与路径保护。
- **执行适配器部署位置（P1-8）**：第一阶段在查询服务进程内作为独立逻辑安全模块，不新增微服务。
- 建执行适配器与强制验证。所有写动作强制：前后快照 → 执行 → 观察窗口 → 后快照 → 对比 → 判决。验证检查真实效果：错误率、延迟、可用性、就绪副本、重启率、服务目标。执行结束只说明命令执行，验证单独输出业务判决。恶化状态停止后续自动操作、提示风险、建议回滚，绝不说修复成功。前后对比用与动作完全相同的上下文与资源。回滚本身是新处置动作，重新走风险与审批，禁止自动执行高级别回滚。
- 门禁：写动作没有验证不能进入成功；恶化能阻断。禁止把容器命令或命令退出码当业务恢复。

## 第十二阶段：前端产品收敛与智能调查页

- 重写信息架构。主导航收敛为六大块：总览；智能运维（智能调查、告警与事件、审批任务）；可观测（服务、链路、日志与指标）；资源（Kubernetes、主机与虚机、容量与硬件）；治理（知识与手册、变更与审计、SLO）；系统管理（用户与权限、设置）。
- 原一级入口——AI 工具、图谱、工作流、K8sGPT、RAG、报告中心、变更时间线、容量预测、独立 Grafana——全部降级为后台能力或嵌进相关页面。
- 新增智能调查工作台，展示结构化过程而非聊天：调查对象、计划与依赖、进度与心跳、每个工具的真实状态与耗时、关键证据与原始数据跳转、根因候选、支持证据、反驳与缺证、二次调查过程、最终根因与置信度拆分、未知项、结构化处置方案与回滚、风险影响与审批状态、执行结果、前后恢复验证、调查历史与审计链。大模型完整文字只出现在"详细分析"区域。前端新增专门接口文件，禁止页面散落直接请求。断线后从运行记录恢复。每个页面显示当前租户集群，调查运行的集群不随全局切换器改变。
- **调查历史分享权限（决策变化）**：V1 支持复制带运行编号的 URL，但访问时重新做 RBAC，仅具备对应租户 / 集群 / 资源权限者能打开，**不支持匿名公开分享**。
- 改造专业页面，增加证据双向跳转。日志页面改成"原始日志 / 异常模式"双视图，异常模式显示模式、基线、当前、增长、首次出现，能跳到原始日志、链路、容器、服务和调查。服务、链路、容器、告警页面增加"交给人工智能调查"。证据跳转用规范资源参数，不传原始查询语句。跳转后重新鉴权。页面捕获错误不能把接口错误静默显示成空列表。跳转复原原证据集群，不用当前全局集群覆盖。
- **Workflow 保留范围（P1-21）**：保留内部 Approval / Execution / Verification orchestration、Run recovery、必要 background jobs；不保留普通用户的 Workflow Designer / Agent Workflow Page / Graph Workflow Debug。管理员可进"系统管理 → 高级"作运行详情 / 诊断，不是产品主入口。
- **管理能力权限（P1-22）**：普通用户不能编辑 Tool Registry、Prompt、Model Provider、Workflow internals、Graph engine config。Graph 业务视图可看，内部配置仅管理员。
- 门禁：人工智能与专业页面双向可追踪；日志异常模式自动运行；主导航收敛；每个核心页面能回答自己的固定问题；两条主旅程不要求用户选工具、代理、工作流。

## 第十三阶段：多集群权限与安全加固

- 建完整权限矩阵文档与测试，覆盖角色、能力、租户、集群、命名空间、资源、动作。
- **JWT / session 不承载 authoritative tenant scope（P0-11）**：请求选择 tenant scope，query-api 每次从 MySQL 校验；允许集群服务端派生。明确管理员、审批人、普通用户读写审批执行边界。
- **删除**：匿名设置、客户端租户信任、本地存储角色授权语义。JWT 只留最小身份（见 4.2）。
- 鉴权流程：租户 → 集群 → 命名空间或资源 → 能力 → 风险动作。未登录返回未登录，已登录被拒返回没权限，不能用成功加空数据隐藏越权。同用户在甲集群可读不代表乙集群可读或可执行。
- 查询服务是外部信任边界；编排服务只信签名的内部上下文。网络策略限制编排服务、数据库、容器接口调用来源。
- 测试覆盖：普通用户篡改角色租户集群、审批人跨集群、管理员、内部头伪造、运行与证据编号猜测。
- 门禁：前端、查询服务、编排服务权限行为一致；服务端可独立阻止所有越权。禁止把前端隐藏按钮当权限完成。

## 第十四阶段：删除旧代码、旧接口、旧页面与双主路径

- 用调用图驱动删除。先搜索所有旧、兼容、回退、弃用、迁移、检查点关键词，再梳理前端导入、路由、请求，后端路由、处理器、调用链，部署引用与测试。
- 凡是调用图为零的旧会话、旧检查点兼容、旧根因、旧工具路由、死路由、死处理器、死页面、死接口封装、状态、样式、测试，全部删除。
- 旧接口切换完成后返回对应状态，不静默代理到不等价新接口。删除所有默认、固定编号、全部兼容时不得破坏规范范围测试。
- **X-Tenant-ID 旧 Header compatibility path 在本阶段删除（P1-11）**（前端已于 Phase 12 迁移）。
- 保留有价值的代码：写前日志、当前恢复、命令策略、容器预检、审计、密钥复用。保留用户现有的未跟踪文件或备份。
- 禁止仅凭文件名含"旧"或"回退"就删。保留用户文件：备份目录、备份归档包、几个根目录说明文档、未跟踪二进制，不得擅自删除。
- 新增清理报告，逐项记录删了什么、删了多少、为什么删。
- 门禁：无新旧双主路径，无明显死代码、死接口、死页面，删除报告可量化。

## 第十五阶段：依赖、镜像上下文与镜像精简

- 审计并锁定依赖。所有服务直接依赖、传递依赖、镜像运行测试都查清。运行、开发、测试依赖分离并锁定可重复版本。
- 删除前端确认无引用的依赖库。删依赖必须经验证，任一构建或测试失败即回滚该删除，不能加回退包掩盖。不得删除多集群运行必需依赖。新依赖要维护活跃、锁定版本、可离线缓存、许可可接受、无已知高危漏洞。禁止只靠搜索导入语句删传递依赖。
- 优化镜像。每个服务加精确排除文件，排除版本目录、虚拟环境、节点模块、测试、覆盖率、文档、备份、归档、临时、旧构建产物、本地缓存。构建去符号去调试，运行时镜像不含编译器、源码、测试、模块缓存。前端只允许全新安装，运行时只含构建产物加服务器。编排服务用多阶段构建与分层依赖、最小运行时，离线资产逐项证明需要。
- 删除重复模型缓存、开发工具、无用系统包。镜像优化不得改变端口、健康检查、接口行为。所有自研容器用非根用户，多数服务用只读根文件系统，编排服务只允许少数显式目录可写。镜像生成软件清单与漏洞报告。
- **镜像 20% baseline 精确化（P1-23）**：Baseline 固定为 Phase 1 对五个自研 runtime images 用同一正式 Dockerfile 构建得到的 `docker image inspect .Size` 总和；最终总和必须 ≤ baseline × 0.80。
- 门禁：所有自研运行镜像总大小至少降低两成且不高于基线，单镜像增长有必要性证据；功能、安全、稳定性、离线运行不受损。禁止为减镜像删掉根证书、时区、必要系统库、健康检查或可靠性工具。

## 第十六阶段：全量自动化测试与固定场景

- 补全测试门禁。补齐缺失的事件采集测试、前端组件接口端到端测试、跨服务集成测试。全量验证命令覆盖：全部测试、编译检查、依赖检查、静态检查、前端类型检查、单元组件测试、生产构建、部署检查、模板生成、镜像干净构建、差异检查、密钥 / 二进制 / 备份 / 运行数据扫描。
- 测试覆盖多集群：同名资源双集群、受限用户、跨集群父运行、错误集群。安全测试覆盖认证、越权、头伪造、审批重放、动作篡改、密钥泄露扫描。禁止用模拟数据通过最终真实验收，模拟只用于单元测试。
- 建十二个固定根因场景：内存溢出、崩溃循环、错误率上升、延迟上升、缓存超时、部署不可用、节点压力、变更导致失败、相似知识案例、权限被拒、工具超时、无数据。
- 每个场景检查完整链路：意图、计划、工具调用、证据、假设、反驳、缺证、补查、根因、置信度、未知项。场景通过运行接口注入问题，不直接写界面模拟。写场景只在隔离测试命名空间、经审批执行。场景用自动断言检查整条链路的返回，不用自然语言关键词。
- 门禁：十二个场景全部链路通过，失败有可复现证据。禁止仅人工阅读最终报告判通过。

## 第十七阶段：精确重置历史运行数据（正式 destructive cleanup）

> **本阶段就是数据清理。所有旧文档 / 注释 / Task / Gate 中的"Phase 16 数据清理""Task 16.x cleanup""Phase 16 DATA_DELETION_MANIFEST"统一改为 Phase 17。**

- **Phase 17 不是再次设计或切换 schema（P0-13）**：新 schema 在 Phase 4/5 已 ACTIVE。Phase 17 只清 Manifest 明确批准的数据。若需为了最终验收清除 Phase 5–16 产生的新-schema 测试运行数据，也必须在 Manifest 单独列明（这是新 schema 上的 pre-acceptance runtime data cleanup，不是因为 schema 又发生迁移）。
- 执行前必须先列出精确的删除清单（DATA_DELETION_MANIFEST）：要清哪些运行时表、哪些 ClickHouse 运行时历史表、哪些 VictoriaMetrics 历史序列、哪些 VictoriaLogs 历史日志、哪些 Chroma 过期集合、哪些 MinIO 运行时历史前缀、哪些运行时存储卷、哪些检查点 / 工作流运行时存储。
- **Secret、证书、credential_ref、有效知识库绝不允许进入 DELETE 清单**。用户、角色、租户、集群、凭据引用、Kubernetes Secrets、证书、大模型配置、数据源配置、有效知识、手册，全部默认标记为 PRESERVE。Manifest 只对运行时 / 历史对象分类为 DELETE / PRESERVE / UNKNOWN，UNKNOWN 禁止删除。Manifest 须区分三类：`OLD_SCHEMA_RESIDUAL`、`NEW_SCHEMA_PRE_ACCEPTANCE_RUNTIME_DATA`、`PERSISTENT_CONTROL_PLANE_DATA`。
- 清理流程：进入 maintenance → 停止 ACTIVE writers → drain WAL/outbox → 对 Manifest 批准对象执行 cleanup → 对 schema / version 做完整性校验 → **仅当 Manifest 明确要求且安全时执行 idempotent init** → restart writers → verify fresh writes。清理期间写接口进维护状态，读接口返回维护，不伪装无数据。
- 任一目标不明确立即停止；部分失败不得继续部署。按租户 + 集群精确确认；验收环境可全清，但不得误清外部或共享集群数据。不打印密钥，备份加密且访问受控。
- 清理后验证：配置、用户登录、大模型配置仍存在；运行历史为空；新结构版本正确。
- **强约束 DATA-CLEANUP-P0-000**：历史运行数据清理的规范标识是阶段名 "Precise Historical Runtime Data Reset"（当前编号 Phase 17）。自动化、审批记录、文档**不得仅依赖阶段编号**，必须同时引用 DATA_DELETION_MANIFEST 的 ID / hash。删除授权措辞固定为「确认执行 DATA_DELETION_MANIFEST: manifest_id=… sha256=… environment=…」，**不是**「确认 Phase 17」。即使将来 Phase 17 又变成 Phase 18，也不会误授权。
- **未获得用户对具体 Manifest 的明确确认，禁止执行任何删除。**

## 第十八阶段：最新源码干净构建与部署

- 工作区是拟交付源码，全量测试新鲜通过。递增正式版本号，用同一版本号构建所有自研镜像。部署新结构、初始化任务与最新镜像。不复用旧版本号、旧镜像，不用临时镜像作最终交付。
- **source identity（P0-15）**：未允许 commit 前，验收构建必须使用唯一 source / build identifier（source_tree_hash / build_id / version / image digest / build_timestamp），**不能伪称 clean Git commit**。正式 clean Git-tag build 延后到用户允许提交之后。
- 流程：正式源码 → 全量测试 → 递增版本 → 干净构建全部镜像 → 检查镜像 → 部署 → 滚动 → 健康与就绪 → 镜像摘要对账。
- 健康与就绪必须验证结构、存储和关键内部依赖，不只进程存活。构建、初始化、滚动任一步失败即停止，不继续真实验收。
- 部署至少配置两个测试集群注册项，凭据来自密钥引用。首次密钥由环境注入，升级复用既有值，日志不显示值。禁止跳过镜像构建用于最终部署。

## 第十九阶段：真实新数据、多集群、大模型与浏览器端到端

- 验证新数据链与多集群。产生测试流量，写入新链路、日志、指标、拓扑；产生容器事件与传感器日志，写入资源事件。然后通过存储 → 查询服务 → 专业界面 → 代理工具 → 证据，全程可端到端关联。
- 无数据必须区分：流量未产生、采集不可用、没权限、查询错误。两个集群生成同名的订单服务，查询、证据、根因、事件推送、审批都不能串。多集群测试用户验证读、拒、动作范围。禁止直接向界面或数据库插入假成功结果。
- 真实大模型验收。管理员已配置真实大模型，不记录密钥。用十个固定问题逐项验收：检查集群健康并给出真实证据、为什么订单服务错误率上涨、自动定位异常日志模式、定位内存溢出的真实根因、是否与最近变更有关、用容器诊断工具参与调查、是否存在相似手册案例、当前证据缺什么、给出处置方案但不执行、修复后如何确认恢复。
- 每个问题记录提供方、模型、运行编号、事件、工具结果、证据、假设、报告。大模型未实际调用、降级模拟、工具不可用或断流，都判失败或部分，不算真实通过。禁止用模拟开关或测试桩做最终验收。
- 浏览器端到端。覆盖所有主页面和关键交互：标签页、弹窗、抽屉、证据跳转、人工智能分析、审批、执行、验证、运行历史、长事件流。保存关键响应状态、运行与证据编号、截图，不保存令牌与密钥。控制台错误、静默捕获、误导空态、网络错误都记录为缺陷。三角色端到端，篡改本地存储角色不能提权。
- 门禁：浏览器端到端全通过，无主页面不可用、断流、错误跳转或越权。产品最终验收的每一项都有真实浏览器、真实角色、真实数据证据；缺任一项就失败。禁止只看到页面加载成功就通过，不操作真实闭环。

## 第二十阶段：缺陷收口与最终干净生产构建

- 收口缺陷。每个缺陷按最小复现、日志、工具结果、证据、网络、调用链定位，按测试先行修复，同步删除被替代旧路径。
- 严重问题：事实冲突或编造、证据不可追踪、根因无证据、日志代理不运行、事件推送断流、权限语义错误、无数据当健康、绕审批、执行即恢复、验证错误、旧镜像、主页面不可用。
- 次要问题：时间集群过滤、证据跳转、变更链路日志容器关联、置信度、菜单未收敛、旧主路径、明显死代码死依赖。
- 修复必须保持契约兼容；契约若变，三端与文档同一次提交更新。安全修复必须含负向测试。门禁：无任何严重和次要问题。
- 最终干净构建、部署、冒烟。重新全量测试、递增正式版本号、构建所有镜像、部署、重新采集新数据、大模型冒烟、浏览器冒烟。输出**最终 source_tree_hash / build_id、版本号、摘要、部署版本、镜像、冒烟运行编号**（未允许 commit 前不得伪称 Git commit；见 P0-15）。
- 最小冒烟覆盖健康、运行创建、事件推送、证据查询、专业页面接口。任一步失败立即退回，不允许标记部分完成。最终冒烟至少验证两个集群的同名资源隔离。正式容器运行最终镜像，遗留问题仍为零，无脏临时镜像。禁止复用上一阶段旧验证结果替代最终构建后冒烟。

## 第二十一阶段：最终文档与 GitHub 同步

- 先出最终交付文档，至少七份：目标架构、实施报告、测试报告、数据模型重设计、代码与依赖清理、镜像大小报告、最终验收报告。

## 7.1 RCA Source Reliability V1 默认值表（P1-5）

| Evidence Source | 默认可靠度 |
|---|---|
| Kubernetes API 当前对象状态 | 0.95 |
| 直接 Metric / SLI 数据 | 0.95 |
| Trace / Span | 0.90 |
| Kubernetes Event | 0.90 |
| 结构化 Change Record | 0.90 |
| Resource Graph 确定性关系 | 0.85 |
| DeepFlow 确定性流量 / 调用观测 | 0.85 |

**三条规则**：
1. source reliability 表示"来源默认可信程度"，不是事实最终置信度。"restartCount=15" 可带 0.95，但"因此 ConfigMap 修改是根因"是推断，不能继承 0.95。
2. 知识 / K8sGPT 永远不能覆盖当前运行事实。优先级：现场直接证据 > 现场派生证据 > 诊断工具 > 知识 / 历史案例 > 大模型推断。
3. 数值锁定在版本化配置。Luna 只能实现这些值，不能为了让测试通过而调高。调值必须走真实 RCA 数据集校准 → 比较准确率 / 误报率 → 改版本化配置 → 回归 12+ RCA 场景，不是 Prompt 调参。

## 7.2 RCA 评分公式与状态判定（P1-4）

```
base_score = LLM reasoning prior × 0.35 + evidence support × 0.30 + source reliability × 0.20 + temporal correlation × 0.15
final_score = base_score − contradiction_penalty − missing_critical_evidence_penalty
```

- confirmed：score ≥ 0.80 且至少一条 high-reliability direct evidence 且无 critical contradiction
- supported：0.60 ≤ score < 0.80
- unknown：score < 0.60 或 critical evidence missing
- rejected：contradiction clearly outweighs support
- **score < 0.60 → 禁止自动 remediation**

high-reliability direct evidence 定义：reliability ≥ 0.85 且证据类型属于现场直接 / 确定性派生观测。Runbook 即使非常匹配也不能单独把假设推成 confirmed。

## 7.3 Planner / Runtime 硬预算（P1-3）

- 计划器：初始步骤 ≤ 12；补查 ≤ 2 轮；总步骤 ≤ 20。
- 运行时超时：默认工具 30 秒、长查询 60 秒、大模型 90 秒、整个运行 900 秒。
- 重试：大模型瞬态重试 2 次、只读工具瞬态重试 1 次、**写操作重试 0 次**。写超时禁止自动重试，必须先查询实际状态。
