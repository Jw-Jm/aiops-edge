## 1. 测试目标

本测试方案用于从**前端页面**对当前 AIOps 系统进行完整验收，最终回答以下五个问题：

1. 前端页面是否能够正常访问、操作和完成全部已设计功能；
2. 页面展示的数据是否来自真实后端数据源，数值、状态、范围和关联关系是否正确；
3. 页面展示是否符合设计预期，包括加载、空状态、异常状态、刷新、筛选、分页、详情和权限提示；
4. AI 能力是否真实调用模型、工具和数据源，是否能够基于真实证据完成故障调查，而不是依赖固定答案、Mock 数据或前端拼接；
5. 系统是否形成设计要求的 AIOps 闭环，并达到可投入真实运维验证的标准。

本方案不以“页面能打开”作为通过标准，也不以“AI 能回答问题”作为 AIOps 可用标准。最终必须验证从用户意图、计划、工具调用、证据、假设、根因到受控动作、验证和审计的完整链路。

## 2. 测试基本原则

### 2.1 前端操作原则

所有正式验收步骤均从浏览器前端页面发起，包括：

- 登录；
- 查询和筛选；
- AI 对话；
- 新建 Investigation；
- 查看 Tool Activity；
- 查看 Evidence；
- 创建、审批和执行受控动作；
- 创建告警规则；
- 查看告警、日志、Trace、容量、硬件和变更；
- 配置模型、集群和用户；
- 查看报告和审计结果。

为制造已知故障而预置的测试 Deployment、Pod、Trace、Log、告警、IPMI 数据等属于**测试环境准备工作**，不计入正式验收步骤。正式验收过程中不得通过直接调用后端 API 替代页面操作。

### 2.2 真实数据原则

正式验收环境必须关闭或禁止影响结论的 Mock、Stub、固定返回值和演示数据。所有需要证明“真实可用”的项目必须能够追溯到真实数据源，例如：

- Kubernetes API；
- Metrics/Prometheus 类数据源；
- ClickHouse Trace；
- Logs 数据源；
- 告警存储；
- MySQL 运行状态和持久化数据；
- Grafana；
- IPMI Exporter；
- 平台配置的真实 LLM；
- K8sGPT；
- 真实的 ToolRun、Evidence、Approval、Audit 记录。

### 2.3 结果可追溯原则

任何 AI 根因结论都必须能够回答：

- 使用了什么工具；
- 查询了哪个集群、Namespace、资源；
- 工具什么时候执行；
- 工具是否成功；
- 返回了什么事实；
- 哪些事实支持当前假设；
- 哪些事实与假设矛盾；
- 哪些证据仍缺失；
- 为什么最终选择该根因；
- 根因置信度依据是什么。

无法追溯到真实 ToolRun 和 Evidence 的 AI 结论不得判为 AIOps 真实可用。

### 2.4 失败真实性原则

数据源、工具或模型不可用时，系统必须真实反映失败状态，禁止：

- 把连接失败显示为“无数据”；
- 把工具失败显示为成功；
- 在无证据时生成确定性根因；
- 使用历史缓存结果冒充当前实时结果；
- K8sGPT 不可用时伪造 K8sGPT 分析结果；
- LLM 不可用时仍显示“模型连接正常”。

### 2.5 设计符合性原则

最终设计符合性按以下链路验收：

```text
Intent
  ↓
Plan
  ↓
ToolRun
  ↓
Evidence
  ↓
Hypothesis
  ↓
Support / Contradiction / Missing
  ↓
Root Cause
  ↓
Action
  ↓
Risk
  ↓
Approval
  ↓
Execution
  ↓
Verification
  ↓
Audit / Timeline
```

若最终冻结设计要求上述完整闭环，则任何一层缺失、伪造或不可追溯，都不得宣称“完全满足设计要求”。


### 2.6 测试失败后的统一排查原则

当任一测试项出现 FAIL/BLOCKED 时，按以下顺序排查，禁止直接从“AI 模型有问题”或“数据源有问题”开始猜测：

1. **确认测试前提**：账号、Cluster、Namespace、资源名称、时间窗、故障注入状态与代码版本必须与测试记录一致；
2. **确认页面现象**：记录页面错误文案、空状态、异常状态、时间戳和截图，确认不是筛选条件、缓存或浏览器状态导致；
3. **确认浏览器请求**：使用浏览器开发者工具 Network 检查对应请求 URL、方法、请求参数、Cluster/Namespace/Run ID、HTTP 状态码、响应体和耗时；不得只依据页面文案定位；
4. **确认 Query API**：核对 query-api 是否收到同一请求、服务端解析出的用户/租户/集群/资源范围是否正确、返回码与前端看到的是否一致；
5. **确认业务组件**：根据测试域继续检查 ai-orchestrator、ingest、LLM proxy、ai-action-executor、Grafana、K8sGPT 等责任组件；
6. **确认真实数据源**：最后核对 Kubernetes API、Metrics、Logs、ClickHouse Trace、MySQL、IPMI 等底层事实，判断问题属于“源数据不存在”“采集错误”“查询错误”“语义转换错误”还是“前端展示错误”；
7. **确认持久化和审计**：涉及 Run、ToolRun、Evidence、Approval、Action、Audit 的问题必须核对 MySQL 中的权威状态是否存在，区分“未生成”“已生成未持久化”“后端存在但前端未展示”；
8. **修复后原场景复测**：修复后必须使用相同账号、对象、故障和时间窗重新执行原测试；P0/P1 不接受只做接口级验证而不回到前端完整复测。

问题定位时按以下责任边界判断：

```text
页面展示/交互问题
    ↓
Browser Network / 前端状态管理
    ↓
query-api：认证、授权、参数、运行态 SoT、查询入口
    ↓
AI 场景：ai-orchestrator → Tool Executor → ToolRun/Evidence
动作场景：Approval/Action SoT → ai-action-executor → Kubernetes WRITE
观测场景：Metrics / Logs / ClickHouse Trace / Kubernetes / IPMI / Grafana
    ↓
MySQL 持久化 / Audit / Timeline
```

## 3. 验收等级与最终判定

### 3.1 五级验收模型

| 等级 | 验收内容 | 通过条件 |
|---|---|---|
| L1 | 前端功能可用 | 页面、路由、控件、权限、错误状态和操作流程均符合预期 |
| L2 | 数据真实可用 | 页面数据与真实数据源一致，无明显缓存、Mock、单位和范围错误 |
| L3 | AI 调查真实可用 | AI 能形成真实 Run、ToolRun、Evidence、Hypothesis 和 Root Cause |
| L4 | 受控动作真实可用 | Preflight、审批、TOCTOU 防护、执行、验证和回滚能力符合设计 |
| L5 | 完整设计符合 | 完整链路、持久化、审计、隔离、安全和异常降级均符合冻结设计 |

### 3.2 最终结论分级

最终报告必须使用以下结论之一，不得只写“测试通过”：

| 结论 | 判定标准 |
|---|---|
| 不可用 | L1 不能通过，或核心页面/登录/数据源不可使用 |
| 页面可用但 AIOps 不成立 | L1、L2 基本通过，但 AI 无真实 ToolRun/Evidence 或无法完成真实调查 |
| AIOps 只读调查可用 | L1～L3 通过，可完成真实诊断，但受控执行闭环尚未完成或未批准 |
| AIOps 受控闭环可用 | L1～L4 通过，读写闭环在批准的测试执行环境完成 |
| 完全满足冻结设计 | L1～L5 全部通过，且无 P0/P1 未关闭问题 |

### 3.3 硬性否决条件

出现以下任一情况，最终不得判为“完全满足冻结设计”：

1. AI 根因无法追溯到真实 ToolRun 和 Evidence；
2. 已知不同故障得到相同固定根因或固定证据；
3. 数据源失败后 AI 仍给出确定性实时结论；
4. Investigation 的 Plan、Hypothesis、Evidence 或 Root Cause 仅为前端静态内容；
5. K8sGPT 被设计为正式能力，但受控故障场景无法产生真实 `k8sgpt_diagnose.v1` ToolRun；
6. Evidence 或 Run 在不应丢失的服务重启后消失；
7. 跨 Tenant、Cluster、Namespace 能读取不属于当前授权范围的数据；
8. 破坏性操作可绕过审批或资源版本校验；
9. 生产默认禁写要求被破坏；
10. 真实执行环境中动作执行后无法验证执行结果或无法恢复；
11. 页面展示的核心指标与源数据不一致且无明确解释；
12. 存在明文演示密码、默认生产账号提示或明显生产安全暴露未整改。

## 4. 当前代码基线的重点审查项

以下内容为基于当前代码静态审查得到的**测试重点**。静态审查不能替代运行时验收，但这些项目必须列为 P0/P1 加严测试。

| 编号 | 当前代码现象 | 风险 | 测试要求 |
|---|---|---|---|
| R-01 | `k8sgpt_diagnose.v1` 已进入 Tool Registry，且镜像包含 K8sGPT 二进制 | 设计已存在，但 Investigation 主执行映射需要实测确认 | 必须用可确定触发 K8sGPT 的故障验证真实 ToolRun |
| R-02 | Investigation 页面当前代码中 Plan/Hypothesis 存在空数组或静态映射迹象 | 可能出现后端有能力、前端却未完整展示 | 必须逐项验证 Plan、Hypothesis、Support/Contradiction/Missing 来自真实 Run |
| R-03 | Evidence Detail 页面存在“内存态登记、进程重启后即失”相关提示 | 证据持久化可能不符合审计要求 | 必须执行服务重启后的 Evidence 持久化测试 |
| R-04 | Changes 页面一次读取固定上限并在前端本地筛选 | 超过上限后可能漏查历史记录 | 必须构造超过 200 条记录进行检索完整性验证 |
| R-05 | 登录页存在演示账号和演示环境提示 | 生产安全与发布质量风险 | 生产候选版本必须验证相关提示已移除或隔离 |
| R-06 | 前端 API Client 仍存在默认 Tenant Header 逻辑 | 可能与已冻结的可信上下文设计不一致 | 必须做跨 Tenant/Cluster 权限与 Header 伪造测试 |
| R-07 | 当前前端自动化测试覆盖有限 | 回归风险较高 | 本文档所列 P0/P1 必须形成可重复验收记录 |
| R-08 | 生产动作执行器设计为默认禁用 | 不能简单按“未执行=失败”判定 | 分别验证生产默认禁写和批准测试环境真实执行闭环 |
| R-09 | Investigation Center 当前存在创建人展示固定为 `system` 的代码迹象 | 运行记录展示可能与真实发起人不一致 | 必须验证 Run 创建人来自真实身份而非前端固定值 |
| R-10 | Investigation 详情中的 Action 存在静态初始化迹象 | 可能出现“页面有动作，但并非真实后端 Action” | 必须验证 Action/Risk/Approval 与当前 Run 后端状态一一对应 |

### 5.1 环境要求

建议使用独立的非生产验收环境，至少包含：

- AIOps 前端；
- query-api；
- ai-orchestrator；
- ingest；
- LLM proxy；
- MySQL；
- ClickHouse；
- Metrics 数据源；
- Logs 数据源；
- Kubernetes 测试集群；
- K8sGPT；
- Grafana；
- KubeVirt；
- IPMI Exporter 或等价硬件测试数据；
- 独立的受控动作执行测试实例。

生产候选环境保持动作执行器默认禁用；另启独立测试执行实例验证真实变更、验证和回滚。

### 5.2 账号准备

至少准备三类账号：

| 账号类型 | 用途 |
|---|---|
| admin | 用户、系统设置、模型、集群、审批和全部页面测试 |
| approver | 审批测试 |
| user | 普通查询、AI Chat、Investigation 和权限隔离测试 |

不得使用共享账号完成全部验收，否则无法验证角色权限。

### 5.3 已知故障场景

在测试 Namespace `aiops-test` 中预置以下故障，每个故障应具有可预先确定的真实根因：

| 场景 | 预期真实根因 | 主要证据 |
|---|---|---|
| F01 | CrashLoopBackOff | Pod 状态、Restart Count、容器日志、Event |
| F02 | OOMKilled | Last State、Exit Code、内存指标、Event |
| F03 | ImagePullBackOff | Pod Event、镜像拉取错误 |
| F04 | FailedScheduling/Pending | Scheduler Event、资源不足或约束不满足 |
| F05 | HTTP 5xx 上升 | Trace、日志、错误率指标 |
| F06 | 高延迟 | Trace duration、P95/P99、应用日志 |
| F07 | 健康服务 | 正常 Pod、正常指标、无异常日志 |
| F08 | 数据源断开 | 明确的 unavailable/error 状态 |

故障场景必须记录真实创建时间、资源名称、Namespace 和预期根因，作为验收对照基线。

# 6. 前端公共功能验收

## TC-COM-01 登录成功

**优先级：P0**

步骤：

1. 打开 `/login`；
2. 使用有效普通用户账号登录；
3. 观察跳转结果；
4. 刷新页面；
5. 重新访问受保护页面。

预期：

- 登录成功后进入 Overview；
- Token/会话保持正常；
- 刷新后不会无故退出；
- 普通用户能访问授权页面；
- 页面不显示错误的 admin 权限入口。

失败条件：登录成功但页面仍跳回 `/login`；刷新后会话丢失；普通用户获得管理员能力。

### 问题排查方案

- **优先排查**：固定当前账号、Cluster、Namespace、对象和时间窗，复现后记录页面现象与浏览器 Network 请求；确认 HTTP 状态码、请求参数和响应体是否符合预期。
- **链路排查**：按 `浏览器 Network → query-api 认证/授权 → 用户/角色持久化` 的顺序逐层核对，找到第一个与上一层事实不一致的位置；若底层事实正确而页面错误，优先定位前端映射/状态管理。
- **典型根因**：缓存键错误、自动刷新覆盖筛选条件或请求竞态；服务端授权缺失、角色缓存未刷新或前端隐藏代替后端鉴权。

- **修复后复测**：修复后必须从本测试项规定的前端入口重新执行全部步骤，并同时保存页面截图和关键 Network 响应；涉及真实数据的项目还要再次与底层事实交叉核对。

## TC-AI-01 真实 ToolRun

**优先级：P0**

步骤：

1. 使用 F01 发起 Investigation；
2. 打开 Run 详情的 Tool Activity；
3. 逐项查看 ToolRun。

预期每个 ToolRun 至少具有：

- tool_id；
- 执行状态；
- 执行时间；
- 目标 Cluster/Namespace/Resource；
- executor/backend；
- 成功或失败信息；
- 与 Run 的真实关联。

失败条件：Tool Activity 为固定演示内容、无 Run 关联或刷新后消失。

### 问题排查方案

- **优先排查**：先看 Tool Activity 对应请求是否返回真实 ToolRun ID；若页面无记录，再确认 query-api 的 Run 查询结果中是否已有 ToolRun。
- **后端链路**：若 query-api 无 ToolRun，检查 orchestrator 是否真正选择工具、是否向正式执行器发起执行、执行结果是否成功回写运行态 SoT。
- **底层核验**：确认工具实际访问了对应 Metrics/Logs/K8s/Trace 数据源，而不是只产生“tool selected”事件。
- **典型根因**：工具只注册未执行；选择事件误当执行事实；ToolRun 写入失败；Run ID 关联错误；前端仍使用静态 Tool Activity。

- **修复后复测**：修复后必须重新创建新的 Run，从前端完整执行本场景，并记录新的 Run ID、ToolRun ID、Evidence ID；不得复用旧 Run 证明修复有效。

## TC-AI-02 Evidence 真实性与交叉验证

- **典型根因**：只在前端隐藏菜单；服务端未做资源范围校验；默认 tenant 回退；Run/Evidence 查询未附带 cluster/tenant ownership 条件。

## TC-E2E-01 Kubernetes 已知故障完整调查

**优先级：P0**

场景：F01 CrashLoopBackOff。

正式前端步骤：

1. 普通用户登录；
2. 进入 AI Chat，描述当前服务异常；
3. 由 Chat 引导进入结构化 Investigation；
4. 创建 Run；
5. 观察 Plan；
6. 观察 Tool Activity；
7. 确认 `query_k8s.v1` 真实执行；
8. 确认受控场景下 `k8sgpt_diagnose.v1` 真实执行；
9. 查看 K8s Evidence；
10. 查看 Logs/Metrics/Trace 等补充 Evidence；
11. 查看 Hypothesis；
12. 查看 Support/Contradiction/Missing；
13. 查看 Root Cause 和 Confidence；
14. 查看推荐 Action 和 Risk；
15. 如动作需要审批，提交审批；
16. approver 登录并批准；
17. 在受控执行测试环境执行动作；
18. 查看 Verification；
19. 返回 K8s 页面确认真实状态；
20. 查看 Audit/Timeline；
21. 重启相关服务后重新打开该 Run 和 Evidence。

必须得到完整链路：

```text
用户故障描述
  ↓
Intent
  ↓
Plan
  ↓
query_k8s.v1
  ↓
真实 Kubernetes Evidence
  ↓
k8sgpt_diagnose.v1
  ↓
真实 K8sGPT 分析
  ↓
Logs / Metrics / Trace 补充证据
  ↓
Hypothesis
  ↓
Support / Contradiction / Missing
  ↓
Root Cause
  ↓
Action + Risk
  ↓
Approval
  ↓
Execution
  ↓
Verification
  ↓
Audit / Timeline
```

### 问题排查方案

- **排查方法**：按链路逐层截断定位，禁止直接跳到最终 RCA。依次确认 Intent→Plan→ToolRun→Evidence→Hypothesis→RCA→Action/Risk→Approval→Execution→Verification→Audit。
- **定位原则**：找到第一个“不满足预期”的层即为主故障点；后续层的失败通常属于级联结果。
- **K8sGPT 专项**：若只有 `query_k8s.v1` 而没有 `k8sgpt_diagnose.v1`，单独记录 K8sGPT 技术路线缺陷，不要把整个 Kubernetes 查询误判为不可用。
- **复测要求**：修复任何一层后必须重新从 Chat/前端入口跑完整链路，不能只单测修复组件。

- **修复后复测**：修复后必须重新创建新的 Run，从前端完整执行本场景，并记录新的 Run ID、ToolRun ID、Evidence ID；不得复用旧 Run 证明修复有效。

# 29. AIOps 真伪判定规则

只有同时满足以下条件，才可以判定“AIOps 真实可用”：

1. AI 对实时问题能够创建真实 Run；
2. Run 中存在真实 ToolRun；
3. ToolRun 能够关联实际数据源；
4. Evidence 可以在源页面独立验证；
5. 已知不同故障产生不同证据与根因；
6. 健康对象不会被强行诊断为故障；
7. 数据源失败时不会生成虚假实时结论；
8. K8sGPT 在规定场景下能够真实执行；
9. Hypothesis、Support、Contradiction、Missing 不是固定模板；
10. Root Cause 能引用 Evidence；
11. Run/Evidence 能按设计持久化；
12. 权限隔离和审计成立。

只有在此基础上，受控执行、审批、验证和回滚也全部通过，才可进一步判定“AIOps 受控闭环可用”。
